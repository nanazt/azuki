# 음성 연결 복구와 봇 재시작 구현 명세

## 근거와 권한

동작 정책은 [음성 연결 복구와 봇 재시작 결정](../adr/0004-voice-recovery-and-bot-restart.md)을 따르고, 재생 복구(Playback recovery)와 봇 재시작(Bot restart)의 의미는 [도메인 용어](../glossary.md)를 사용해요.
사용자가 확정한 목적지·자동 재개·접근 권한·시간 제한을 아래의 구현 및 검증 계약으로 구체화해요.
인터페이스 경로, 상태 표현, 저장 일관성, 작업 소유권은 이 정책을 만족시키기 위한 기술적 선택이며 새로운 사용자 승인을 요구하는 별도 제품 정책은 아니에요.
이 문서는 명세 작성의 결과이며 코드 구현, 배포, 테스트용 Discord 서버 조작 또는 원격 쓰기의 승인을 뜻하지 않아요.
이후 요청한 로컬 구현과 검증 결과, 사용자 담당 실험의 남은 항목은 [실행 티켓의 구현 기록](voice-recovery-and-bot-restart-tickets.md#구현-기록과-사용자-확인)에 구분해 기록해요.

## 문제와 완료 결과

사용자는 봇 자체가 다시 살아나도 음성 채널에 자동으로 돌아오지 않는 현상을 보고했어요.
변경 전 `crates/azuki-bot/src/handler.rs`는 `Ready` 및 일부 재생 이벤트에서 기본 채널에 접속했지만, 지속적인 음성 연결 복구와 봇 작업 재생성을 소유하는 경로는 없었어요.
같은 파일의 `start_bot`은 오디오 구독 작업을 생성한 뒤 핸들을 보관하지 않아, 단순한 함수 재호출만으로 이전 작업 정리와 중복 재생 방지가 보장되지 않았어요.

변경 전 `crates/azuki-player/src/actor.rs`의 재생 위치는 재생 상태의 경과 시간을 사용하며 음성 연결 여부를 반영하지 않았어요.
`crates/azuki-db/src/queries/queue.rs`는 현재 곡과 대기열 및 반복 모드를 별도로 저장했고, 현재 곡에는 위치와 재생·일시정지 구분이 없었어요.
구형 복구 경로의 `PlayerController::with_state`는 저장된 현재 곡을 0초·일시정지로 복원했어요.
따라서 접속 호출을 한 번 더 하는 변경만으로는 재생 복구를 충족할 수 없어요.

완료 결과는 연결 해제나 봇 중단 이후 기본 음성 채널에 자동 복귀하고, 사용자가 마지막으로 지정한 재생 상태를 이어 쓰는 것이에요.
웹과 Discord에서는 같은 봇 재시작 기능을 호출하고 동일한 진행 상태와 제한을 관찰해요.
명령 접수, Discord 연결, 음성 연결, 재생 복구 완료를 구분하며, 접수만으로 성공을 표시하지 않아요.

## 확정한 동작과 범위

| 항목 | 계약 |
|---|---|
| 복구 계기 | 음성 연결 단절, 사람이 Discord에서 실행한 ‘연결 끊기’, 봇 작업 종료, azuki 프로세스가 다시 시작된 경우를 포함해요. |
| 복귀 목적지 | 서버 설정의 기본 음성 채널이에요. 마지막으로 머문 채널은 복구 목적지로 저장하지 않아요. |
| 재생 중 | 듣던 곡의 중단 위치부터 자동 재개하고 남은 대기열을 보존해요. |
| 일시정지·대기 | 일시정지 상태와 위치를 유지하고, 현재 곡이 없는 경우 임의로 곡을 시작하지 않아요. |
| 강제 종료 | 정상적인 저장이 지속되던 상황에서 마지막 저장 위치로 최대 약 5초 되감기는 것을 허용해요. 장애 동안의 시간을 더하지 않아요. |
| 자동 재시도 | 성공할 때까지 계속하며 시도 간격을 늘려요. 간격 상한은 300초이고 총 시도 횟수나 총 복구 시간의 제한은 없어요. |
| 수동 재시작 | 웹 서버 설정의 제어와 `/restart`를 제공하고 Discord 봇 및 음성 처리만 교체해요. |
| 접근 권한 | 웹은 기존 인증으로 접근 가능한 모든 사용자, Discord는 설정된 서버의 명령어 사용자가 대상이에요. 관리자·역할·음성 채널 참여 조건은 추가하지 않아요. |
| 중복·대기 | 진행 중인 재시작은 하나로 합치고, 새 요청 접수부터 서버 공통 30초 동안 다음 재시작을 받지 않아요. 웹·Discord 및 사용자 사이에 제한을 공유해요. |

기존 서버 설정의 관리자 전용 항목과 기존 인증·멤버십 판정은 유지해요.
빈 채널 자동 퇴장, 복구 기록의 시간 만료, 재접속을 끄는 새 제어, 다중 Discord 서버 지원은 추가하지 않아요.
Discord에서 봇을 다른 채널로 이동시키는 동작 자체를 새로운 강제 복귀 계기로 확대하지 않으며, 다음 복구의 목적지는 기본 채널이에요.
기본 채널 설정 변경이 현재 연결을 즉시 이동시키는 기능으로 확대되지 않아요.

봇 재시작 중에도 HTTP 서버, 로그인, 기존 WebSocket 연결, 플레이어와 대기열 및 진행 중인 미디어 작업의 수명은 유지해요.
웹까지 중단된 상태에서 버튼이나 명령어로 azuki 프로세스·컨테이너를 되살리는 기능은 제외해요.
전체 프로세스가 외부 수단으로 다시 기동되면 저장된 상태의 복구는 이번 범위에 포함해요.
실제 음원 오류 처리, 재생 이력 및 청취 시간의 기존 의미는 바꾸지 않고, 연결 장애를 곡의 정상 종료로 취급하지 않아요.

## 연결과 재시작을 소유하는 모듈

봇의 수명, 재시작 요청 직렬화, 음성 복구 및 재시도 상태를 한 모듈에서 소유해요.
외부 인터페이스는 재시작 요청과 최신 상태 구독으로 제한하고, 웹이나 명령어가 직접 Songbird 객체 또는 프로세스 종료 토큰을 조작하지 않아요.
`crates/azuki/src/main.rs`의 조립 지점에서 기존 채널 기반 의존성 주입 방식으로 이 인터페이스를 연결해요.
웹에 Discord SDK 수명 관리 책임을 넣거나 이를 위해 새로운 공통 크레이트를 만들지 않아요.
플레이어 상태의 소유권은 기존 `PlayerController`와 액터에 남겨요.

### 수명과 교체

전체 애플리케이션 종료와 봇 한 세대의 종료를 분리해요.
각 봇 세대는 Discord 클라이언트, Songbird, 오디오 구독 작업 및 그 세대의 콜백과 재시도 작업을 소유해요.
기존 세대의 오디오와 작업을 중단하고 종료를 확인하기 전에 새 세대가 같은 재생 출력을 소유하면 안 돼요.
공유된 Songbird 및 Discord HTTP 참조도 현재 세대와 일치시키고, 늦게 끝난 이전 세대가 새 참조를 지우거나 덮어쓰지 못하게 해요.

봇 작업이 오류·예기치 않은 반환·패닉으로 끝나면 웹이 살아 있는 수명 관리자에서 이를 관찰하고 복구해요.
음성 연결만 끊긴 경우에는 먼저 음성 연결을 복구하며, 모든 음성 실패마다 Discord 클라이언트나 azuki 전체를 재시작하지 않아요.
Discord 연결이 유지된 채 음성만 끊기는 경우와 Discord 세션 전체가 바뀌는 경우를 모두 처리해요.

네트워크 연결, 재생 준비, 종료 대기에는 취소와 유한한 대기 제한을 적용해요.
시간 제한 뒤에도 이전 출력 소유권이 정리되지 않았다면 새 출력을 중복 생성하지 않고 실패를 드러내요.
전체 애플리케이션 종료는 자동 복구나 사용자 재시작보다 우선하고, 종료 도중 봇을 다시 생성하지 않아요.
수명 관리 루프 자체를 웹 재시작 요청을 처리하는 Discord 클라이언트 작업 안에 넣지 않아요.

### 연결 확인과 재시도

Songbird의 길드 통화 객체 존재나 Discord `Ready`만으로 음성 연결 및 재생 복구 성공을 판정하지 않아요.
현재 봇 세대, 목적지 채널, 실제 음성 연결 완료 및 최신 재생 상태와의 일치를 확인해요.
이전 연결의 지연된 성공·실패 이벤트는 현재 상태를 바꿀 권한이 없어요.

자기 봇의 Discord 음성 상태 변경과 Songbird 드라이버의 연결·재연결·단절 신호를 현재 세대에 묶어서 처리해요.
라이브러리 내부의 짧은 재연결 시도와 애플리케이션의 재시도 타이머가 서로 독립적으로 입장을 반복하지 않게 해요.
라이브러리의 최종 실패 통지만 기다리느라 내부 재시도 동안 재생 시계가 계속 진행되는 구현은 허용하지 않아요.
현재 명령어의 직접 입장과 `Ready`·재생 이벤트의 자동 입장 경로도 같은 연결 소유권 아래로 이관하고, 서로 다른 코드가 동시에 복구하지 않게 해요.

처음 복구 계기에는 즉시 한 번 시도해요.
실패 후 대기 간격은 기술적 기본값으로 `1, 2, 4, 8, …, 256, 300, 300, …`초를 사용해요.
300초는 한 시도가 종료된 뒤 다음 시도까지의 최대 대기 간격이며, 개별 연결 시도는 별도의 유한한 시간 제한을 가져요.
연결 및 필요한 재생 복구가 확인된 뒤에만 연속 실패 횟수를 초기화해요.
빠른 재실행 루프, 여러 타이머의 중복 시도, 자동 실패 때문에 재사용 대기를 계속 연장하는 동작은 금지해요.

매 시도는 현재 기본 채널 설정을 사용해요.
기본 채널이 없거나 형식이 유효하지 않으면 `unconfigured`로 표시하고 Discord 입장 요청을 보내지 않아요.
설정 변경 시 복구를 재평가하되, 관리자 전용 설정 변경 권한을 재시작 권한으로 대체하지 않아요.
채널 삭제나 권한 부족은 실패 원인으로 표시하고, 임의의 다른 채널로 우회하지 않은 채 설정과 권한이 다시 유효해질 기회를 계속 확인해요.
같은 실패가 계속돼도 위 간격 제한을 지켜요.

### 재시작 요청의 수명

요청 판정과 접수 시각 기록은 단일 소유자에서 원자적으로 처리해요.
진행 중이면 기존 작업에 합치는 판정이 재사용 대기 판정보다 우선해요.
합친 요청과 거부한 요청은 추가 재시작을 예약하지 않고 접수 시각도 연장하지 않아요.
진행 중이 아니면서 마지막 접수 후 30초가 지나지 않았다면 남은 시간을 알려주고 거부해요.
내부 시간 비교에는 단조 시간을 사용해요.

진행 중인 재시작은 기존 세대 정리와 새 세대의 구동을 넘기는 유한한 교체 작업을 뜻해요.
새 세대의 Discord·음성 연결 재시도가 무기한 계속된다는 이유로 `restart_in_progress`를 영구 유지하지 않아요.
교체 작업의 성공 또는 실패 뒤에는 이 표시를 해제하며, 30초가 지났다면 사용자가 다시 재시작할 수 있어요.
이 표시 해제는 음성 복구 성공 표시와 별개예요.

자동 복구와 수동 요청도 같은 소유자에서 직렬화해요.
수동 요청이 접수되면 기존 대기 타이머와 시도는 취소하거나 같은 교체 흐름에 통합하고, 독립적인 두 복구 흐름을 만들지 않아요.
전체 프로세스 재시작을 넘어 사용자 재시작의 30초 제한이나 지난 요청 목록을 영속화하지 않아요.
이 제한은 운영 중인 공유 봇을 보호하는 제한이며 모든 방해 행위를 차단하는 정책은 아니에요.

## 재생 상태와 저장 일관성

### 재생 의도와 실제 진행

사용자가 지정한 재생·일시정지 의도와 음성 출력이 가능한 상태를 구분해요.
연결 장애나 재시작으로 출력을 중단할 때 현재 곡, 위치, 재생 의도를 액터의 한 시점에서 확보하고 진행 시간을 정지해요.
내부 복구를 위해 사용자의 일시정지 조작을 가장하거나, 복구 성공을 사용자의 새 재생 요청으로 취급하지 않아요.

연결을 기다리는 동안에는 재생 시간이 늘지 않고 자동으로 다음 곡으로 넘어가지 않아요.
웹의 위치 표시와 청취 시간 집계도 이 중단 구간을 재생된 시간으로 취급하지 않아요.
필요한 중단 여부를 기존 플레이어 스냅샷과 이벤트에 표현해 프런트엔드의 시간 보간도 멈춰요.
복구 상태의 표현 때문에 기존 플레이어 버튼이 재생 의도를 변경할 수 없게 만들지 않아요.

복구 도중의 일시정지·재개·탐색·건너뛰기·중지·대기열 변경은 기존 액터 순서대로 처리해요.
재개는 연결 전이라도 재생 의도를 갱신할 수 있지만, 음성이 준비되기 전부터 시계를 진행시키지는 않아요.
복구는 가장 최근의 곡·위치·의도에 수렴하며, 장애 직전의 복사본으로 사용자 조작을 덮어쓰지 않아요.
복구용 출력 준비가 끝난 사이에 상태가 바뀌었다면 최신 상태를 다시 적용하고, 이전 준비 결과를 현재 재생으로 확정하지 않아요.

음성 단절이나 출력 교체 때문에 발생한 종료 이벤트는 곡의 정상 완료와 구분해요.
봇 세대와 재생 인스턴스의 식별을 함께 확인하고, 이전 출력의 지연된 종료 이벤트로 다음 곡을 꺼내거나 현재 곡을 지우지 않아요.
같은 곡 반복 재생도 서로 다른 재생 인스턴스이므로 곡 ID 비교만으로 해결하지 않아요.
출력 복원 자체는 새로운 곡 시작 이력, 추가한 사용자 변경, 대기열 제거·회전 또는 중복 청취 기록을 만들지 않아요.
고정 지연 뒤 탐색하거나 볼륨·일시정지를 적용하는 작업도 같은 세대와 재생 인스턴스를 확인하거나 교체 시 취소해요.
종료 콜백만 보호하고 늦은 탐색 작업이 새 재생을 바꾸도록 남기지 않아요.

정상 재시작은 현재 출력의 진행을 멈춘 시점의 위치를 사용해요.
음성 단절은 해당 출력에서 신뢰할 수 있는 마지막 진행 위치를 기준으로 삼고, 단절 감지 이후의 대기 시간을 더하지 않아요.
봇의 출력 위치와 사용자의 Discord 클라이언트가 실제로 수신한 마지막 오디오 샘플은 구분하며, 후자의 전달 확인을 새로 만드는 범위는 아니에요.
네이티브 출력 위치·단절 감지·탐색의 실제 오차는 실행 검증에서 별도로 측정해요.

### 복구 스냅샷

현재 곡 식별자와 추가한 사용자, 위치, 재생 의도, 남은 대기열 순서 및 각 항목의 추가한 사용자, 반복 모드를 액터의 일관된 스냅샷으로 확보해요.
기존 곡별 볼륨·메타데이터와 재생 이력의 저장 의미는 유지해요.
현재 곡은 액터의 재생 상태에서 가져오며 대기열 첫 항목을 현재 곡으로 해석하지 않아요.
전체 반복 모드가 순환을 위해 대기열에 현재 곡의 항목을 남긴 경우 이를 중복 오류로 간주해 제거하지 않아요.
프로세스 내에는 상태 순서를 비교할 수 있는 단조 버전을 두어 늦은 저장이나 출력 준비가 최신 상태를 덮어쓰지 못하게 해요.
실제 저장 형식과 버전의 정수형은 구현에서 정하되, `Instant`나 단절 이후의 경과 시간을 영속 위치로 저장하지 않아요.

재생이 진행되는 동안 정상 저장 사이의 간격이 5초를 넘지 않도록 위치를 주기적으로 저장해요.
곡 교체·일시정지·재개·탐색·중지·대기열 및 반복 모드 변경, 복구를 위한 진행 정지 때에도 최신 스냅샷 저장을 요청해요.
변경 요청과 주기 저장은 하나의 순서로 처리하고, 더 오래된 스냅샷이 나중에 커밋되지 않게 해요.
5초는 정상 저장 시 마지막 성공한 체크포인트의 위치 손실 상한을 뜻하며, DB 장애·프로세스 정지·음원 탐색 오차까지 성공으로 숨기는 보장이 아니에요.

현재 곡, 대기열, 반복 모드는 하나의 SQLite 트랜잭션에서 같은 스냅샷으로 커밋해요.
곡 이동 도중 강제 종료해도 이전의 완전한 상태 또는 이후의 완전한 상태가 복원돼야 하며, 곡은 바뀌고 대기열만 이전 상태인 조합은 허용하지 않아요.
기존 `queue_items`와 `app_config` 저장 구조를 우선 사용하고, 상태를 별도로 계속 쓰는 기존 경로는 새 저장 경로로 일원화해요.
변하지 않은 대기열을 위치 체크포인트마다 지우고 다시 삽입하는 불필요한 작업은 피하되, 트랜잭션의 상태 일관성은 유지해요.

정상 봇 재시작과 정상 프로세스 종료에는 종료 전 최신 상태의 저장 완료를 기다려요.
봇만 재시작하는 동안에는 살아 있는 액터가 계속 권위 있는 상태이며 DB에서 오래된 상태를 다시 읽어 덮어쓰지 않아요.
저장 실패가 봇 교체를 무기한 막지 않게 하되, 실패 사실과 마지막 저장 상태를 드러내고 정상 저장이 완료됐다고 표시하지 않아요.
저장 실패 중에는 메모리 상태로 봇 복구를 계속할 수 있지만, 그 사이의 프로세스 강제 종료에도 약 5초 복구를 보장한다고 표시하면 안 돼요.

## 외부 인터페이스

### 상태 표현

HTTP와 WebSocket은 같은 최신 봇 상태를 사용해요.
아래 필드는 새 인터페이스의 기술적 계약이며, 구현 내부의 Discord SDK 객체는 노출하지 않아요.

| 필드 | 의미 |
|---|---|
| `revision` | 해당 프로세스에서 증가하는 상태 버전이에요. 클라이언트는 같은 연결 수명에서 더 오래된 응답으로 최신 상태를 덮어쓰지 않아요. |
| `status` | `starting`, `restarting`, `connecting`, `retry_wait`, `ready`, `unconfigured`, `failed`, `stopped` 중 하나예요. |
| `target_voice_channel_id` | 현재 복구 목적지인 Discord 채널 ID 문자열 또는 `null`이에요. |
| `restart_in_progress` | 유한한 봇 교체 작업이 진행 중인지를 나타내요. 음성 재시도 전체의 진행 여부와는 달라요. |
| `restart_available_at` | 새 수동 재시작의 시간 제한이 끝나는 UTC Unix 밀리초 또는 제한이 없을 때 `null`이에요. 진행 중 여부는 별도로 확인해요. |
| `next_retry_at` | 다음 자동 시도 예정인 UTC Unix 밀리초 또는 예약이 없을 때 `null`이에요. |
| `last_error` | 연결·재생 복구 오류가 없으면 `null`, 있으면 `stage`, `code`, `message`를 가진 정보예요. `stage`는 `bot`, `voice`, `playback` 중 하나예요. |
| `last_checkpoint_at` | 마지막으로 복구 스냅샷을 정상 커밋한 UTC Unix 밀리초 또는 아직 없으면 `null`이에요. |
| `persistence_error` | 아직 해결되지 않은 저장 오류의 안전한 `code`, `message` 또는 `null`이에요. 연결 오류와 독립적으로 유지해요. |

`ready`는 현재 목적지의 음성 연결이 확인되고 최신 재생 의도가 반영된 상태예요.
일시정지나 현재 곡 없음도 의도대로 복원됐다면 `ready`일 수 있어요.
`retry_wait`는 포기한 상태가 아니며 재시도 예정 시각을 함께 제공해요.
`failed`는 교체·준비 작업의 실패를 뜻하고 무기한 자동 시도 중단 정책을 새로 만들지 않아요.
저장 오류는 연결 상태와 별개로 표시할 수 있으며, 연결 복구 성공이 해결되지 않은 저장 오류까지 지우지는 않아요.

오류 정보에는 토큰, 쿠키, Discord HTTP 인증 정보, 내부 경로가 포함된 원문 예외를 그대로 보내지 않아요.
안정적인 오류 코드와 사용자에게 안전한 설명을 사용하고, 상세 원인은 기존 서버 로그로 확인해요.
프로세스가 교체되거나 WebSocket이 다시 연결되면 클라이언트는 이전 연결의 버전 비교 기준을 버리고 새 최신 상태에서 시작해요.
연결 수명이 바뀌기 전에 시작한 HTTP 조회의 늦은 응답은 새 연결의 상태로 적용하지 않아요.

### HTTP와 상태 전달

| 경로 | 성공 계약 |
|---|---|
| `GET /api/bot/status` | 기존 인증을 통과하면 현재 상태의 200 JSON을 반환해요. Discord에 직접 조회하거나 복구를 시작하지 않아요. |
| `POST /api/bot/restart` | 새 요청은 `outcome: accepted`, 진행 중 요청에 합친 경우는 `outcome: already_restarting`과 현재 `status` 객체를 포함한 202 JSON을 반환해요. |

재시작 POST는 서버에 설정된 봇만 대상으로 하며 클라이언트가 길드·채널·사용자 ID나 재시도 간격을 지정하지 않아요.
기존 인증과 CSRF 검사를 재사용하고 `X-Requested-With: XMLHttpRequest`를 요구해요.
상태 GET의 비로그인 요청과, 올바른 CSRF 헤더를 가진 재시작 POST의 비로그인 요청은 401이에요.
POST의 CSRF 헤더가 없거나 잘못됐으면 기존 선행 미들웨어가 로그인 여부와 무관하게 403으로 거부해요.
기존 멤버십 검사에 의한 거부도 403이며, 일반 사용자라는 이유만으로 403을 반환하지 않아요.
기존 `/api/admin/*`와 설정 변경 경로의 관리자 권한은 그대로 유지해요.

진행 중이 아니면서 30초 대기 중이면 429와 초 단위 올림값의 `Retry-After`를 반환해요.
본문은 기존 오류 응답의 `error` 문자열을 유지하고 `retry_after_seconds`를 추가해 남은 시간을 전달해요.
수명 관리자가 사용할 수 없거나 애플리케이션이 종료 중이어서 요청을 받지 못하면 503이며, 단순히 Discord 봇이 오프라인이라는 이유로 복구 요청을 거부하지 않아요.
요청이 접수된 뒤 브라우저나 연결이 사라져도 이미 접수한 작업을 취소하지 않아요.
응답과 상태 조회에는 `Cache-Control: no-store`를 적용해요.

기존 `WebEvent`와 WebSocket 통로에 `bot_status` 이벤트를 추가하고 같은 상태 객체를 전달해요.
초기 접속·재접속·이벤트 누락 후 재동기화에서도 최신 봇 상태를 전달해 과거 이벤트 수신 여부에 의존하지 않아요.
기존 플레이어 이벤트 순서, 인증 재검증, 전체 로그아웃 및 웹 종료 동작을 유지해요.
`WebSeqEvent`의 순번은 기존 통합 발행 경로에서 부여하고 봇이 별도의 순번으로 같은 통로에 끼어들지 않아요.
봇 상태의 `revision`과 전체 WebSocket 이벤트 순번은 서로 다른 비교 기준이에요.
별도 WebSocket 연결이나 상태를 계속 확인하는 두 번째 폴링 경로는 만들지 않아요.

### Discord 명령어와 화면

설정된 서버에 `/restart`를 등록하고 웹과 같은 수명 관리 인터페이스를 사용해요.
명령 처리 단계에서도 대상 서버를 확인하되 관리자 권한이나 음성 채널 참여는 요구하지 않아요.
Discord 자체의 명령어 접근 설정을 우회하는 기능은 제공하지 않아요.

상호작용 응답 제한 안에 먼저 응답을 확보한 뒤 작업을 넘기며, 명령 처리 작업이 자기 자신이 속한 봇의 종료 완료를 기다리게 하지 않아요.
요청 접수·이미 진행 중·남은 재사용 대기·접수 실패를 구분해 요청자에게 알려줘요.
접수 응답을 복구 완료 메시지로 표현하지 않아요.
응답 확인 직후 연결이 끊겨도 같은 요청을 추가 접수하거나 재시작을 되돌리지 않아요.
봇이 명령어를 받지 못하는 상태에서는 웹이 복구 수단이고, 웹까지 죽었을 때 동작한다고 안내하지 않아요.

웹 서버 설정에는 관리자 여부와 무관하게 볼 수 있는 봇 제어 영역을 두고 기존 관리자 전용 설정과 분리해요.
버튼 이름은 전체 웹 서버 재시작과 구분되는 ‘Discord 봇 재시작’ 의미를 사용해요.
현재 상태, 안전한 실패 이유, 다음 시도 예정 및 재사용 대기를 보여줘요.
진행 중에는 중복 조작을 막고, 교체가 끝났지만 음성 재시도 중인 경우 30초 대기가 끝나면 다시 요청할 수 있어요.
비관리자에게 기존 관리자 전용 설정값을 조회하거나 보여주는 방식으로 제어 영역을 구현하지 않아요.

재생 화면의 시간 보간은 음성 복구 대기 동안 멈추며, 재생·일시정지 의도와 복구 대기 상태를 혼동하지 않게 표시해요.
정상적인 출력 교체 중에도 재생 시계는 멈추지만, 봇 상태가 `ready`이면 복구 대기 문구는 표시하지 않아요.
출력 중단 플래그와 봇 수명 상태를 함께 사용하며, 봇 상태가 아직 확인되지 않았거나 실제 복구·재시작 중이면 기존 대기 표시를 유지해요.
복구 문구는 일반 플레이어 배경용 경고 전경색을 사용하며, 다크·라이트 모드 모두 작은 글자 기준 최소 4.5:1 대비를 확보해요.
프런트엔드 문자열은 기존 `ko.ts`를 먼저 작성하고 `en.ts`를 함께 갱신해요.
봇 응답은 `messages.rs`의 한국어·영어 구조를 사용해요.
새 번역 프레임워크나 별도의 봇 전용 화면을 도입하지 않아요.

## 저장 형식 전환과 호환성

새 복구 기록은 형식 버전을 명시하고 재생 의도와 위치가 실제로 기록된 데이터인지 구분해요.
기존 `now_playing`처럼 곡과 사용자만 있는 기록은 새 형식의 재생 중 상태로 추정하지 않고 기존처럼 0초·일시정지로 복원해요.
이전 데이터에 없던 위치를 복구했다고 주장하지 않아요.
전환은 기존 대기열, 반복 모드, 곡과 사용자 정보를 삭제하지 않아요.
구형 데이터 읽기는 이 데이터 전환에만 필요한 호환 처리이며 별도의 구형 저장 경로를 계속 유지하지 않아요.

필수 값이 누락되거나 형식이 손상된 새 복구 기록을 정상적인 자동 재개로 보완하지 않아요.
새 기록의 위치는 음수가 아닌 밀리초 정수로 검증하고, 유효한 정수지만 곡 길이를 넘으면 기존 플레이어 스냅샷의 의미에 맞춰 곡 길이로 제한해요.
파싱할 수 없는 위치나 알 수 없는 재생 의도는 이 보정의 대상이 아니에요.
복구 오류를 알리고 무관한 유효 데이터는 보존하며, 잘못된 위치·재생 의도로 소리를 내지 않아요.
음원 파일 누락 같은 실제 음원 오류는 연결 장애와 구분하고 기존 음원 오류 처리 범위를 유지해요.
문제가 있는 음원을 재생하지 못했는데 전체 재생 복구가 성공했다고 표시하지 않아요.

정상 저장이 가능할 때 새 복구 상태로 전환하고, 이후 저장과 복원은 새 단일 경로를 사용해요.
스키마 변경이 필요하면 기존 마이그레이션 순서를 따르고 적용된 마이그레이션을 수정하지 않아요.
새로운 복구 상태와 상태 이벤트를 사용하는 프런트엔드·백엔드는 함께 배포하는 기존 방식을 유지해요.
외부 연동용 구형 이벤트 별칭이나 이중 쓰기 경로를 추가하지 않아요.

## 관찰 가능한 완료 기준

| 시나리오 | 관찰할 결과 |
|---|---|
| 재생 중 음성 단절 | 기본 채널에 자동 복귀해 같은 곡을 신뢰 가능한 중단 위치부터 이어요. 대기 중 시간이 진행되거나 다음 곡으로 넘어가지 않아요. |
| Discord의 강제 연결 끊기 | 별도의 사용자 조작 없이 기본 채널에 다시 들어와요. 마지막으로 옮겨졌던 다른 채널을 복구 목적지로 삼지 않아요. |
| 일시정지 또는 곡 없음 | 채널은 복구하되 자동으로 소리를 내지 않아요. 일시정지 위치와 대기열을 유지해요. |
| 봇 작업 종료와 프로세스 재기동 | 봇 작업 종료는 살아 있는 수명 관리자가 복구하고, 프로세스 재기동은 DB의 새 복구 상태를 사용해요. 두 경로를 각각 확인해요. |
| 강제 종료 후 복원 | 실제 주기 저장이 진행된 뒤 저장 주기의 서로 다른 지점에서 종료해요. 마지막 정상 저장과 중단 위치 차이가 약 5초 이내이며 곡·대기열·반복 모드가 한 상태로 복원돼요. |
| 수동 재시작 | 웹과 `/restart` 각각에서 접수 후 봇 세대만 교체되고, 로그인·HTTP·기존 WebSocket·대기열은 살아 있어요. 출력은 한 개예요. |
| 혼합 동시 요청 | 웹 두 요청과 Discord 요청이 겹쳐도 한 번만 교체해요. 진행 중 합친 요청은 다음 작업을 예약하거나 30초 기준을 연장하지 않아요. |
| 재사용 대기 경계 | 접수 후 30초 직전의 새 요청은 거부하고, 경계 이후에는 받아요. 자동 실패와 다른 사용자의 거부 요청이 대기를 연장하지 않아요. |
| 긴 장애와 회복 | 재시도 간격이 300초에 도달한 뒤에도 계속 시도해요. 권한 복구 후 별도 조작 없이 연결돼요. 음성 실패가 계속돼도 수동 재시작은 영구 잠기지 않아요. |
| 무효 목적지 | 미설정·삭제·권한 부족을 구분 가능한 실패로 보여주고 다른 채널에 들어가지 않아요. 복구 중 바뀐 설정은 다음 시도에 반영해요. |
| 복구와 사용자 조작 경합 | 일시정지·탐색·건너뛰기·중지가 출력 준비와 겹쳐도 마지막 액터 상태가 이겨요. 같은 곡 반복과 이전 세대의 늦은 종료 이벤트도 대기열이나 이력을 중복 변경하지 않아요. |
| 저장 경합과 오류 | 이전 저장이 늦게 끝나도 최신 상태를 되돌리지 않아요. 트랜잭션 도중 오류에는 혼합된 현재 곡·대기열이 복원되지 않아요. 저장 실패를 정상 체크포인트로 표시하지 않아요. |
| 접근 및 정보 보호 | 비관리자 성공, 상태 GET 및 올바른 CSRF 헤더를 가진 POST의 비로그인 401, 로그인 여부와 무관한 잘못된 CSRF 헤더의 403, 기존 멤버십·관리자 설정의 403을 각각 확인해요. 오류에 비밀값이 노출되지 않아요. |
| 상태 동기화와 UI | 상태 이벤트를 놓치거나 다시 연결해도 최신 상태와 재사용 대기를 복원해요. 한국어·영어 및 일반 사용자 화면에서 접수와 복구 완료를 구분해요. |
| 구형 기록과 전체 종료 | 구형 기록은 0초·일시정지로 복원하고, 전체 앱 종료 중에는 새 봇이나 재시도 작업이 생성되지 않아요. |

## 검증 방식과 실행 의존성

실제 Discord 실험은 사용자가 직접 수행하기로 했어요.
에이전트는 실제 Discord에 연결하지 않는 로컬 자동 검증과 브라우저 확인, 재현 절차 및 관찰 항목 준비를 맡아요.
테스트 봇의 실제 접속·입장·연결 해제·재시작과 청취 확인은 사용자 담당이며, 에이전트가 이를 직접 조작하거나 자동화하지 않아요.
에이전트의 구현·로컬 검증 완료와 사용자의 실제 Discord 확인 완료는 구분해서 기록해요.

플레이어의 기존 `controller_tests.rs`를 확장해 중단 중 시계 정지, 최신 조작 우선, 같은 곡의 오래된 종료 이벤트와 반복 모드를 검증해요.
수명 관리 모듈의 실제 인터페이스를 통해 제어 가능한 시간과 연결 결과를 입력하고, 단일 출력 소유권·요청 합치기·30초 경계·300초 상한·종료 우선순위를 검증해요.
실패를 주입하는 테스트용 연결 어댑터는 제어 상태의 검증에만 사용하며 실제 Discord 음성 복구를 증명한 것으로 취급하지 않아요.

SQLite 검증은 실제 저장·재읽기를 사용하고, 부분 실패를 주입해 트랜잭션 일관성과 구형 기록 전환을 확인해요.
메모리 스냅샷을 그대로 반환하는 테스트만으로 강제 종료 복구를 검증하지 않아요.
HTTP는 `crates/azuki-web/tests/common/mod.rs`의 `TestApp`과 `tower::ServiceExt::oneshot`을 사용해 인증, 응답 의미, 공유 제어와 DB 부수 효과를 검증해요.
플레이어 동작 자체를 HTTP 통합 테스트에 중복 구현하지 않아요.
WebSocket 초기 상태·누락 복구·기존 연결 유지 검증은 실제 업그레이드 가능한 테스트 연결을 사용해요.

사용자는 Discord 테스트 서버와 채널, 구간을 구별할 수 있는 음원을 사용해 강제 연결 끊기, 연결 장애, 봇 작업 종료, 프로세스 강제 종료 및 수동 재시작을 각각 관찰해요.
중단 전후의 곡과 위치, 중복 출력 여부, 대기열, 재생 이력, 웹 연결을 함께 확인해요.
정상 연결만으로 성공을 판단하거나, 원래 단절 경로에 도달하지 않은 실험을 장애 복구 증거로 사용하지 않아요.
실제 브라우저에서 일반 사용자·관리자와 한국어·영어 화면을 확인하고, 봇 재시작 도중 웹 제어와 상태 갱신이 살아 있는지 관찰해요.

구현 완료 검사는 저장소 규칙에 따라 `mise run check`, `mise run test`, `frontend`에서 `npx tsc --noEmit` 후 `npm run build`를 실행해요.
영구 테스트는 위의 상태 전이·경계·경합·오류 계약을 보호하는 경우에 남기고, 실제 실행용 임시 코드와 음원은 검증 후 제거해요.
사용자의 실제 Discord 확인 결과가 아직 없으면 해당 항목을 미검증으로 보고하며, 모의 연결 테스트로 네이티브 음성 복구가 검증됐다고 대체하지 않아요.
독립적인 로컬 구현·검증은 계속하고, 실제 기술 설계에 필요한 미확인 관측만 해당 작업의 의존성으로 남겨요.

구현은 먼저 기존 액터의 재생 의도·진행 정지·일관된 저장을 갖추고, 그 계약을 소비하는 봇 수명 및 음성 복구를 연결하는 순서예요.
웹과 명령어는 같은 제어 및 상태 인터페이스가 정해진 뒤 각각 연결할 수 있어요.
마지막 통합 검증은 음성 복구·작업 교체·저장·두 사용자 경로가 모두 연결된 상태에서 수행해요.
각 단계는 같은 전체 범위의 의존 순서이며 일부 단계만으로 사용자 요구가 완료됐다고 보지 않아요.

## 남은 기술적 확인

추가로 결정해야 할 제품 정책은 없어요.
`Cargo.lock`의 Songbird 포크는 `25195877c715e08df25eda668df6b3a6bb3d3cdf`에 고정돼 있어요.
해당 로컬 소스의 `src/events/core.rs`에서 `DriverConnect`, `DriverReconnect`, `DriverDisconnect`를 확인했고, 앞의 두 이벤트는 드라이버 연결 성공을 나타내요.
`src/events/context/data/disconnect.rs`의 실패 정보는 내부 재시도 소진 뒤 수집될 수 있으므로, `DriverDisconnect`를 항상 즉각적인 단절 신호로 가정하지 않아요.
이 소스 확인은 이용할 수 있는 신호의 근거이며 실제 오디오 출력이나 모든 단절 경로의 이벤트 시점을 검증한 결과는 아니에요.

구현은 같은 포크의 `src/driver/retry/mod.rs`에서 문서화한 `driver_retry.retry_limit = Some(0)`을 사용해 드라이버 연결 시도를 한 번으로 제한하고, 애플리케이션 수명 관리자가 무기한 백오프를 소유해요.
드라이버 연결 제한 시간은 15초예요.
성공한 드라이버 재연결과 관리자 설정 변경도 현재 DB의 기본 채널을 다시 검증하는 복구 경로로 들어가요.
이 선택은 소스로 확인한 재시도 소유권이며, 내부 소프트 재연결 중 실제 단절 신호가 전달되는 지연이나 청취 위치 오차를 측정한 결과는 아니에요.

사용 중인 포크에서 단절 감지와 내부 재시도가 겹칠 때의 실제 이벤트 순서, 출력 위치 및 탐색 정확도는 사용자의 실제 Discord 실험 결과로 확인해요.
연결 이벤트의 세부 순서를 가정해 위의 상태·권한·저장 계약을 약화하지 않아요.
개별 연결·종료 대기의 구체적인 시간 제한과 상태 메시지의 세부 문구는 위 계약 안에서 정하는 지역적 구현 선택이에요.
이 명세 작성 시점에는 실제 장애 원인을 확정하거나 재접속·재생 위치·UI를 실행 검증하지 않았어요.
