# 음성 연결 복구와 봇 재시작 실행 티켓

## 계획 깊이와 사용법

[구현 명세](voice-recovery-and-bot-restart.md)를 실행 가능한 로컬 티켓 7개로 나눠요.
사용자 결정은 [ADR](../adr/0004-voice-recovery-and-bot-restart.md), 재생 복구(Playback recovery)와 봇 재시작(Bot restart)의 의미는 [도메인 용어](../glossary.md)가 기준이에요.
명세의 계약을 이 문서의 축약된 설명으로 대체하거나 범위를 줄이지 않아요.

핵심 재생 상태와 봇 수명은 결합돼 있지만, 네이티브 관측 실험과 저장·복원은 먼저 병행할 수 있고 공통 제어 이후의 사용자 경로도 독립적으로 진행할 수 있어요.
따라서 실험 1개, 동작을 끝까지 연결하는 변경 5개, 경로가 결합되는 실제 장애 검증 1개로 구성해요.
DB·백엔드·프런트엔드처럼 계층만 나눈 티켓이나 컴파일만 되는 준비 작업은 만들지 않아요.

기존 로컬 티켓 저장 관례가 없어 명세와 같은 디렉터리의 이 문서를 실행 기록으로 사용해요.
`VRC-*`는 이 문서 안의 식별자이며 GitHub 이슈 번호가 아니에요.
사용자의 후속 구현 요청에 따라 로컬 코드를 구현했으며, 아래의 실행 기록은 구현·로컬 검증과 사용자 담당 Discord 실험을 구분해요.
이 문서의 상태 기록은 실제 Discord 조작·배포·원격 이슈 생성 권한을 추가하지 않아요.
완료 기록에는 실제 관찰·검증 결과와 남은 한계를 남기며, 티켓 상태 변경만으로 명세 충족을 주장하지 않아요.

## 의존성과 공통 실행 계약

| 티켓 | 관찰 가능한 결과 | 필요한 선행 산출물 |
|---|---|---|
| [VRC-01](#vrc-01) | 단절·재연결·출력 위치를 신뢰할 수 있게 관측하는 경로를 확인해요. | 없음 |
| [VRC-02](#vrc-02) | 프로세스 재기동 뒤 저장된 곡·위치·재생 의도를 실제 출력까지 복구해요. | 없음 |
| [VRC-03](#vrc-03) | 웹을 유지하며 봇 세대를 안전하게 교체하고 종료된 봇 작업을 자동으로 되살려요. | VRC-02 |
| [VRC-04](#vrc-04) | 음성 단절 뒤 기본 채널로 계속 복귀하고 최신 재생 의도를 이어요. | VRC-01, VRC-03 |
| [VRC-05](#vrc-05) | 일반 로그인 사용자도 웹 설정에서 봇 재시작과 상태 확인을 해요. | VRC-03 |
| [VRC-06](#vrc-06) | Discord 서버 멤버가 `/restart`로 같은 재시작을 요청해요. | VRC-03 |
| [VRC-07](#vrc-07) | 실제 장애와 웹·Discord 혼합 요청에서도 전체 복구 계약이 유지되는지 확인해요. | VRC-04, VRC-05, VRC-06 |

의존성은 티켓의 완료 표시가 아니라 아래에서 정의한 실제 인터페이스·동작·근거를 뜻해요.
VRC-01과 VRC-02는 서로를 기다리지 않아요.
VRC-03의 제어 계약을 인수하면 VRC-04·VRC-05·VRC-06은 서로를 기다리지 않고 진행할 수 있어요.
VRC-07은 결합된 경로를 검증하는 작업이며, 다른 티켓을 시작하기 위한 일괄 승인 단계가 아니에요.

VRC-02는 액터가 소유하는 일관된 복구 스냅샷, 재생 의도와 진행 정지, 최신 상태 순서, 저장 완료·오류 결과를 제공해요.
현재 곡·추가한 사용자·위치·의도·대기열·반복 모드의 의미와 구형 데이터 전환은 명세를 그대로 따라요.
이 계약은 내부 API 이름을 먼저 가정하지 않고 기존 `PlayerController`의 직렬화된 명령과 스냅샷 경로에서 구현해요.

VRC-03은 세대 소유권, 유한한 교체 작업, 서버 공통 30초 대기, `accepted`·`already_restarting`·재사용 대기·미가용 판정과 상태 구독을 제공해요.
상태 필드와 시간 단위는 명세의 외부 인터페이스를 따라요.
VRC-04·VRC-05·VRC-06은 이를 소비하며 자체 재시작 엔진·대기 판정·별도 출력 소유자를 만들지 않아요.
VRC-03에서 상태를 만들고 VRC-05에서 기존 WebSocket 발행 경로로 연결하는 책임을 구분해요.

병행 작업에서는 `main.rs`의 조립·이벤트 발행 등 공유 접점에 통합 담당자 한 명을 정하고 해당 변경을 직렬화해요.
같은 파일을 동시에 편집할 수 있다는 이유로 기능 전체를 불필요하게 선후 관계로 묶지는 않아요.
서로 다른 인터페이스를 임의로 도입하지 않고, 변경이 필요한 실제 계약만 먼저 조율해요.
각 티켓 안에서는 새 경로를 사용하는 모든 호출부를 이관하고 해당 변경이 없앤 구형 쓰기·입장·콜백 경로를 남기지 않아요.

실제 Discord 실험은 사용자가 직접 수행하고, 에이전트는 로컬 자동 검증과 재현 절차·관찰 항목 준비를 맡아요.
이 역할 구분은 VRC-01·VRC-07뿐 아니라 VRC-02부터 VRC-06까지의 실제 Discord 접속·재시작·음성 확인에도 적용해요.
에이전트는 실제 봇을 접속·입장·연결 해제·재시작시키거나 해당 조작을 자동 실행하지 않아요.
로컬 실행과 브라우저 확인은 실제 Discord에 연결하지 않는 환경에서 수행해요.
사용자 실험에는 조작할 수 있는 테스트 봇·서버·채널이 필요하며, 사용자에게 절차와 예상 결과 및 확인할 정보를 인계해요.
에이전트의 구현·로컬 검증 완료와 사용자의 실제 Discord 확인 완료를 별도로 기록해요.
사용자 결과를 기다린다는 이유로 독립적인 로컬 구현·검증까지 중단하지 않고, 기술 설계에 실제로 필요한 미확인 관측만 선행 조건으로 유지해요.
소스 읽기나 모의 연결 결과는 실제 음성 관찰을 대신하지 않아요.
사용자의 실험 수행은 에이전트의 Discord 조작이나 운영 서버 변경·배포 권한을 부여하지 않아요.

## VRC-01 — 네이티브 단절과 재생 위치의 관측 경로를 검증해요

**근거:** [명세](voice-recovery-and-bot-restart.md)의 연결 확인과 재시도, 재생 의도와 실제 진행, 남은 기술적 확인을 따라요.
**선행 산출물:** 없으며 바로 시작할 수 있어요.
**담당:** 에이전트가 소스 근거·재현 절차·관찰 항목을 준비하고, 사용자가 실제 Discord 조작과 청취·관측을 수행해요.
에이전트는 전달받은 결과를 해석해 후속 기술 계약에 반영해요.

이 티켓은 기능 구현이 아니라 VRC-04의 감지·시간 정지 설계를 결정하는 제한된 실험이에요.
사용 중인 Songbird 커밋 `25195877c715e08df25eda668df6b3a6bb3d3cdf`를 기준으로 자기 봇의 음성 상태, 드라이버 연결 이벤트, 트랙 진행 및 종료 이벤트를 함께 관측해요.
검증할 가설은 라이브러리 내부 재시도와 애플리케이션의 복구를 겹치게 만들지 않으면서, 무음 대기를 재생 시간으로 더하지 않을 관측 경로를 확보할 수 있다는 것이에요.
`DriverDisconnect`가 항상 즉각적인 단절 신호라는 가정이나 통화 객체 존재를 연결 성공으로 보는 가정에서 출발하지 않아요.

**관찰 가능한 완료 기준**

- 승인된 테스트 서버에서 정상 재생·일시정지, Discord 강제 연결 끊기, 통신 단절과 회복, 재생 중 출력 교체가 실제로 발생했음을 확인해요.
- 단절·내부 재시도·성공 신호·마지막 신뢰 가능한 진행 위치·트랙 종료의 순서와 시간을 기록해요.
- 초기 음성 연결과 중단 위치 탐색, 같은 곡 출력 교체를 구분하고 늦은 종료·탐색 작업의 영향을 확인해요.
- 내부 재시도 중 진행 시간을 정지할 수 있는 관측 지점과 애플리케이션 재시도와의 소유권 관계를 제안해요.
- 가설이 성립하지 않으면 실패한 경로와 필요한 기술 변경을 명시해요.
  모의 연결이나 다른 정상 경로의 성공으로 대체하지 않아요.

**검증과 인계:** 구간을 구별할 수 있는 음원과 재현 가능한 조작 순서, 의존성 버전, 안전하게 정리한 이벤트·위치 결과를 이 티켓의 실행 기록에 남겨요.
영구 기능이나 검증용 사용자 명령어를 추가하지 않고, 실험만을 위한 테스트를 영구 테스트로 남기지 않아요.
VRC-04는 실험 완료 표시가 아니라 사용 가능한 감지·진행 정지 전략을 인수해요.
부정적인 결과로 그 전략이 없다면 해당 의존성은 여전히 미충족이며, 사용자 계약을 조용히 완화하지 않고 기술 설계로 돌아가요.
VRC-02의 초기 연결 후 저장 상태 복원은 이 단절 관측 실험에 의존하지 않아요.

## VRC-02 — 프로세스 재기동 후 저장된 재생 상태를 이어 써요

**근거:** [명세](voice-recovery-and-bot-restart.md)의 재생 상태와 저장 일관성, 저장 형식 전환과 호환성을 따라요.
**선행 산출물:** 없으며 바로 시작할 수 있어요.

기존 액터의 상태에서 일관된 복구 스냅샷을 얻고, 실제 SQLite 저장과 시작 시 읽기 및 초기 음성 출력까지 연결해요.
새 기록은 재생 의도·위치·현재 곡·대기열·반복 모드를 보존하고, 현재 곡을 대기열 첫 항목에서 추정하지 않아요.
새 기록이 재생 중이면 초기 음성 출력이 준비된 뒤 그 위치에서 시작하고, 일시정지·곡 없음이면 임의로 재생하지 않아요.
이벤트 구독 전에 발생한 시작 이벤트를 기다리는 방식이 아니라 현재 액터 상태를 기준으로 초기 출력을 복원해요.
이 티켓은 저장 라이브러리만 추가하고 끝나는 작업이 아니에요.

액터에 출력 불가에 따른 진행 정지와 사용자 재생 의도를 구분하는 계약을 두고, 초기 연결을 기다리는 동안 시계를 정지해요.
이 상태에서도 재생·일시정지·탐색·건너뛰기·중지를 기존 순서로 처리하며 늦은 출력 준비가 최신 조작을 덮어쓰지 못하게 해요.
플레이어 이벤트·스냅샷과 웹의 기본 위치 보간, 청취 시간 집계도 같은 정지 의미를 사용하게 해요.
지속적인 네이티브 단절 감지와 재입장 스케줄은 VRC-04의 범위이고, 여기서는 그 처리가 소비할 실제 상태 계약과 초기 기동 경로를 완성해요.

**관찰 가능한 완료 기준**

- 새 체크포인트를 가진 프로세스를 다시 기동하면 기본 채널의 초기 연결 성공 뒤 같은 곡과 위치·의도를 복원해요.
  초기 연결 대기 시간을 위치에 더하지 않아요.
- 재생 중 정상 커밋 간격은 5초를 넘지 않고 상태 변경 시에도 저장해요.
  강제 종료 후 저장 상태의 위치 손실은 정상 저장 조건에서 약 5초 이내예요.
- 현재 곡·대기열·반복 모드를 한 트랜잭션에서 커밋하며, 곡 전환 도중 실패해도 앞뒤 상태가 섞이지 않아요.
- 지연된 과거 저장이 최신 상태를 덮어쓰지 않고, 전체 반복의 정상적인 순환 항목을 잘못 제거하지 않아요.
- 정상 종료는 마지막 상태의 저장을 기다리며 저장 실패와 마지막 정상 저장 시점을 드러내요.
  봇 재시작이 소비할 저장 오류 결과도 제공해요.
- 구형 기록은 데이터 손실 없이 0초·일시정지로 복원해요.
  새 기록의 잘못된 의도·위치는 정상 자동 재개로 보완하지 않고, 유효한 정수 위치의 길이 상한은 명세를 따라요.
- 복원 자체가 새 곡 이력·대기열 회전·추가한 사용자 변경을 만들지 않아요.
  최신 일시정지·중지 등 사용자 조작과 현재 곡 없음도 보존해요.

**검증과 인계:** 기존 `controller_tests.rs`의 실제 상태 전이와 스냅샷 경로, 실제 SQLite 트랜잭션·재읽기·부분 실패를 사용해요.
순서가 어긋난 저장과 곡 전환 중 실패가 잘못된 구현을 실제로 구별하도록 검증해요.
프로세스를 새로 기동해 음성 출력과 웹 위치를 확인하고, 메모리 객체를 다시 반환하는 검사만으로 복원을 증명하지 않아요.
기존 독립 저장 경로를 단일 스냅샷 저장으로 이관하며 이중 쓰기나 별도 복구 엔진을 남기지 않아요.
VRC-03에는 살아 있는 액터의 복구·저장 인터페이스를 인계하고, 봇만 교체할 때 DB의 과거 상태를 다시 적용하지 않는 기준도 전달해요.

<a id="vrc-03"></a>
## VRC-03 — 웹을 유지하며 봇 세대를 교체하고 자동 재기동해요

**근거:** [명세](voice-recovery-and-bot-restart.md)의 연결과 재시작을 소유하는 모듈, 재시작 요청의 수명, 상태 표현을 따라요.
**선행 산출물:** VRC-02의 진행 정지·최신 상태 복원·저장 완료와 오류 계약이 필요해요.

단일 수명 관리자가 기존 애플리케이션의 봇을 소유하도록 연결하고, 봇 작업의 예기치 않은 반환·오류·패닉을 관찰해 자동으로 새 세대를 시작하게 해요.
같은 모듈에 외부에서 요청할 수 있는 봇 교체와 최신 상태 구독을 제공해요.
독립적으로 호출할 수 있는 인터페이스만 만들고 실제 시작·종료 경로를 그대로 두는 준비 작업으로 끝내지 않아요.

봇 세대마다 Discord 클라이언트·Songbird·오디오 구독 및 지연 작업을 소유해요.
전체 종료와 세대 종료를 분리하고, 이전 출력을 중단하고 관련 작업 종료를 확인한 뒤에만 새 출력을 허용해요.
공유 HTTP·Songbird 참조와 콜백을 현재 세대에 묶고, 직접 입장 경로도 같은 소유권으로 이관해요.
초기 연결과 저장 상태 복원에는 VRC-02의 실제 경로를 사용하고, 지속적인 음성 단절 감지·재입장 계기는 VRC-04에서 확장해요.

**관찰 가능한 완료 기준**

- 실제 봇 작업을 종료시키면 HTTP·로그인·기존 WebSocket·플레이어·미디어 작업을 유지한 채 자동으로 봇을 다시 구동해요.
  정상 네트워크에서 이전 의도를 재생 출력까지 복원해요.
- 실제 수명 관리 인터페이스로 수동 재시작을 접수해도 같은 교체 경로를 사용해요.
  출력·구독자·지연 탐색 작업이 중복되거나 이전 세대가 새 상태를 변경하지 않아요.
- 여러 요청은 한 교체로 합치며 접수부터 공통 30초를 적용해요.
  합친 요청과 거부한 요청은 시간을 연장하거나 다음 교체를 예약하지 않아요.
- 자동 실패 재시도에는 명세의 증가 간격과 300초 상한을 적용해요.
  자동 실패가 사용자 재사용 대기를 연장하지 않아요.
- 교체 작업은 유한하게 성공·실패하고, 이후 연결 재시도가 계속돼도 `restart_in_progress`를 영구 유지하지 않아요.
  30초 뒤 새 요청을 받을 수 있어요.
- 종료·연결 준비에는 취소와 유한한 대기가 있고, 정리가 실패했을 때 출력을 중복 시작하지 않아요.
  전체 앱 종료 중에는 자동 재기동이 일어나지 않아요.
- 명세의 상태 DTO를 생산하며 접수·교체·연결·재생 복구 완료를 구분해요.
  저장 오류는 연결 오류와 별개로 유지하고 안전한 오류 정보만 내보내요.

**검증과 인계:** 제어 가능한 시간과 봇 작업 결과로 경합·30초 경계·지연된 이전 세대·종료 우선순위를 검증해요.
실제 실행의 수명 관리 인터페이스에 요청하고 실제 봇 작업 종료도 유발해, 교체 전후 출력과 웹 수명이 유지되는지 확인해요.
검증을 위한 영구 공개 엔드포인트를 추가하지 않아요.
VRC-04에는 세대별 음성 작업 소유권과 재시도·상태 발행 계약을, VRC-05·VRC-06에는 공통 요청 판정과 상태 구독을 인계해요.
웹에 Discord SDK 수명 관리를 넣거나 새 공통 크레이트를 만드는 작업은 포함하지 않아요.

## VRC-04 — 음성 단절 뒤 기본 채널에서 재생을 계속 복구해요

**근거:** [명세](voice-recovery-and-bot-restart.md)의 연결 확인과 재시도, 재생 의도와 실제 진행, 관련 완료 기준을 따라요.
**선행 산출물:** VRC-01의 사용할 수 있는 단절·진행 위치 관측 전략과 VRC-03의 실제 세대·복구·재시도 인터페이스가 필요해요.
VRC-05·VRC-06의 사용자 제어가 없어도 진행할 수 있어요.

현재 세대의 자기 봇 음성 상태와 네이티브 연결 신호를 수명 관리자에 연결해, 살아 있는 프로세스에서 음성만 끊긴 경우를 자동 복구해요.
내부 재시도가 끝나는 동안 플레이어 시간이 계속 진행되지 않게 하고, 최신 사용자 의도로 출력을 다시 구성해요.
통화 객체가 남아 있는 단절도 처리하며, 정상 트랙 종료와 연결 장애·출력 교체의 종료 이벤트를 구분해요.

**관찰 가능한 완료 기준**

- 네트워크 단절과 Discord 강제 연결 끊기 모두 기본 채널로 자동 복귀해요.
  마지막으로 옮긴 채널로 복귀하거나 채널 이동 자체를 새 강제 복귀 계기로 삼지 않아요.
- 재생 중이면 신뢰 가능한 중단 위치부터 이어 듣고, 일시정지·현재 곡 없음이면 소리를 내지 않아요.
  대기 중 시간·청취량·대기열이 자동 진행되지 않아요.
- 첫 시도는 즉시 실행하고 실패 뒤 간격을 늘리되 최대 300초로 계속 시도해요.
  라이브러리 내부 재시도와 별개의 중복 입장 흐름을 만들지 않아요.
- 미설정·무효 설정에는 입장 요청을 보내지 않고, 삭제·권한 부족에는 안전한 원인과 재시도 상태를 제공해요.
  다른 채널로 우회하지 않고 다음 시도에 최신 설정을 반영해요.
- 복구 준비와 일시정지·재개·탐색·건너뛰기·중지가 겹쳐도 최신 액터 상태가 이겨요.
  같은 곡의 과거 종료·지연 탐색도 새 재생을 바꾸지 않아요.
- 음성만 실패했다고 매번 봇 전체를 교체하지 않으며, 수동 교체와 음성 복구가 겹치면 같은 소유자가 직렬화해요.
  종료 중에는 재입장하지 않아요.

**검증과 인계:** VRC-01의 실제 단절 절차를 구현에 다시 적용하고 음원 위치·대기열·이력·정지 상태를 함께 관찰해요.
결정적인 시간·결과 제어로 300초 상한, 최신 설정, 과거 콜백과 새 사용자 조작의 순서 양쪽을 검증해요.
실제 음성 진행·탐색 오차와 감지 지연은 별도로 기록해요.
VRC-05의 표시 로직을 다시 구현하지 않고 기존 상태 DTO로 결과를 내보내며, 실제 복구 절차와 실패 조건을 VRC-07에 인계해요.

## VRC-05 — 웹 서버 설정에서 누구나 재시작과 상태 확인을 해요

**근거:** [명세](voice-recovery-and-bot-restart.md)의 외부 인터페이스, HTTP와 상태 전달, Discord 명령어와 화면을 따라요.
**선행 산출물:** VRC-03의 공통 재시작·상태 인터페이스와 상태 DTO가 유일한 코드 선행 조건이에요.
VRC-04·VRC-06에는 의존하지 않아요.

기존 인증·멤버십 판정을 통과한 모든 사용자가 서버 설정에서 ‘Discord 봇 재시작’ 제어와 최신 상태를 보게 해요.
관리자 전용 설정과 제어 영역을 분리하고, 비관리자에게 기존 관리자 전용 설정값을 조회하거나 노출하는 방식으로 만들지 않아요.
웹 어댑터는 공통 인터페이스만 사용하며 별도 교체·30초 대기·음성 복구 엔진을 만들지 않아요.

`GET /api/bot/status`와 `POST /api/bot/restart`를 실제 수명 관리자에 연결해요.
GET은 조회만 하고, POST는 명세의 접수·합침 202, 429와 `Retry-After`·`retry_after_seconds`, 미가용 503을 구분해요.
봇 오프라인 자체를 접수 거부 사유로 삼지 않으며 브라우저가 사라져도 접수된 교체를 취소하지 않아요.
상태·응답에 `no-store`를 적용하고, 안정적인 코드와 안전한 설명을 사용하며 저장 오류와 연결 오류를 독립적으로 표현해요.

기존 `WebEvent` 통로에 `bot_status`를 연결하고 초기 접속·재접속·이벤트 누락 후에도 최신 상태를 보내요.
전역 `WebSeqEvent` 순번과 봇 상태의 `revision`을 구분하고, 이전 연결 수명에서 시작한 HTTP 조회가 새 상태를 덮어쓰지 못하게 해요.
별도 WebSocket이나 두 번째 상태 폴링 경로를 추가하지 않아요.

**관찰 가능한 완료 기준**

- 일반 사용자와 관리자 모두 기존 인증 범위에서 실제 재시작을 요청할 수 있어요.
  기존 관리자 설정의 403 보호는 유지돼요.
- 상태 GET 및 CSRF 형식이 올바른 비로그인 POST는 401이에요.
  없거나 잘못된 POST CSRF 헤더는 로그인 여부와 무관하게 403이고 기존 멤버십 거부도 유지돼요.
- 접수·합침·대기·미가용 응답이 실제 공통 판정과 일치해요.
  토큰·쿠키·Discord 인증 정보·내부 경로를 오류로 노출하지 않아요.
- 버튼과 상태는 유한한 교체, 계속되는 음성 재시도, 복구 완료, 무효 설정, 저장 실패를 구분해요.
  음성 재시도 중에도 교체가 끝나고 30초가 지나면 다시 요청할 수 있어요.
- 누락·재연결 후에도 최신 상태와 재사용 대기를 복원하고, 봇 재시작 중 기존 웹 연결과 플레이어 이벤트·인증 재검증은 유지돼요.
- 한국어·영어 및 일반 사용자·관리자 화면에서 접수와 복구 완료를 구분해요.
  기존 `ko.ts`·`en.ts` 구조를 사용해요.

**검증과 인계:** 기존 `TestApp`·Router `oneshot`으로 인증·응답 계약과 공유 제어의 효과를 확인하고, 실제 업그레이드 가능한 WebSocket으로 초기 상태와 누락 복구를 검증해요.
실제 수명 관리자에 연결한 개발 실행을 브라우저에서 확인하며 모의 UI만으로 완료하지 않아요.
VRC-06과의 혼합 요청 및 모든 네이티브 장애의 결합 검증은 VRC-07에서 수행해요.

## VRC-06 — Discord 서버 멤버가 `/restart`를 사용해요

**근거:** [명세](voice-recovery-and-bot-restart.md)의 재시작 요청 수명, Discord 명령어와 화면, 수동 재시작 완료 기준을 따라요.
**선행 산출물:** VRC-03의 공통 재시작·상태 인터페이스가 유일한 코드 선행 조건이에요.
VRC-04·VRC-05에는 의존하지 않아요.

설정된 서버에 길드 범위 `/restart`를 등록하고 기존 Discord 명령어 접근 설정상 유효한 모든 사용자가 사용할 수 있게 해요.
관리자·역할·음성 채널 참여 조건을 추가하지 않고, 명령 처리에서도 대상 길드를 확인해 DM이나 다른 길드 요청을 전달하지 않아요.
Discord 자체의 접근 설정을 우회하지 않아요.

상호작용 응답 제한 안에 최초 응답을 확보한 뒤 같은 수명 관리자에 요청해요.
명령 처리 작업이 자신이 속한 봇 세대의 종료·교체 완료를 기다리지 않게 해요.
공통 판정의 접수·이미 진행 중·남은 재사용 대기·미가용을 기존 `messages.rs`의 한국어·영어 메시지로 구분해요.
접수 응답을 복구 완료로 표현하지 않고, 응답 뒤 연결이 끊겨도 같은 요청을 재접수하거나 취소하지 않아요.

**관찰 가능한 완료 기준**

- 승인된 테스트 서버에서 음성 채널에 없는 일반 멤버도 명령을 사용해요.
  접수 응답 뒤 실제 봇·음성 세대만 교체되고 HTTP·로그인·WebSocket·플레이어·대기열은 유지돼요.
- DM·다른 길드 요청은 교체를 시작하지 않고, Discord 접근 설정상 사용할 수 없는 사용자의 권한을 새로 열지 않아요.
- 동시에 사용하거나 재사용 대기 중 다시 사용하면 공통 결과를 보여주고 추가 교체·대기 연장·자기 종료 대기 교착을 만들지 않아요.
- 한국어·영어에서 결과의 의미와 남은 시간을 정확히 전달해요.
  테스트는 고정 문구가 아니라 관찰 가능한 결과를 검증해요.
- Discord 명령을 수신하지 못하는 오프라인 상태에서는 웹이 복구 수단임을 안내하며, 이 명령이 죽은 전체 프로세스나 컨테이너를 되살린다고 주장하지 않아요.

**검증과 인계:** 대상 길드 가드와 공유 제어의 효과, 응답 선행 및 자기 종료 비대기를 결정적인 명령 처리 검증으로 확인해요.
승인된 실제 서버에서도 최초 응답과 정상 재시작을 관찰하고, 웹·Discord 혼합 경쟁은 VRC-07에 인계해요.
별도의 Discord 전용 재시작·대기 상태나 영구 검증 명령어는 만들지 않아요.

<a id="vrc-07"></a>
## VRC-07 — 실제 장애와 혼합 재시작에서 전체 복구를 검증해요

**근거:** [명세](voice-recovery-and-bot-restart.md)의 관찰 가능한 완료 기준 및 검증 방식 전체를 사용해요.
**선행 산출물:** VRC-04의 실제 음성 복구, VRC-05의 실제 웹 경로, VRC-06의 실제 Discord 경로가 필요해요.
**담당:** 에이전트가 로컬 통합 검증과 사용자 확인 절차 준비를 맡고, 사용자가 실제 Discord 장애·혼합 요청 실험과 청취 확인을 수행해요.
이 티켓은 앞선 티켓이 자신의 검증을 미루는 장소가 아니라, 독립적인 경로가 결합됐을 때만 확인할 수 있는 위험을 담당해요.

**관찰 가능한 완료 기준**

- 실제 음원이 재생되는 상태에서 웹의 복수 요청과 Discord 요청을 겹쳐 하나의 봇 교체와 공통 30초 제한을 관찰해요.
  응답 상실 뒤 이미 접수된 요청도 중복되지 않아요.
- 교체 중 음성 단절, 긴 권한 오류, 복구 중 최신 재생 조작, 전체 앱 종료를 각각 겹쳐 출력 중복·곡 자동 건너뛰기·과거 상태 회귀가 없음을 확인해요.
- 긴 장애에서 300초 상한에 도달한 뒤에도 시도하고, 문제가 풀리면 자동 복귀해요.
  그동안 웹 재시작 제어가 영구 잠기지 않아요.
- 서로 다른 체크포인트 시점의 실제 프로세스 강제 종료와 재기동에서 약 5초 위치 손실, 곡·대기열·반복 모드의 일관성, 재생·일시정지·곡 없음의 구분을 확인해요.
- 구형 기록, 부분 저장 실패와 네이티브 단절을 결합해 데이터 오류가 잘못된 자동 재개나 거짓 성공 표시로 이어지지 않음을 확인해요.
- 일반 사용자·관리자 및 한국어·영어 브라우저에서 상태·대기·저장 오류와 기존 관리자 보호를 확인해요.
  기존 WebSocket, 로그인, 진행 중 미디어 작업도 봇 교체를 견뎌요.

**검증과 인계:** VRC-01·VRC-04의 재현 절차를 재사용하고, 각 시나리오가 실제 목표 상태에 도달한 증거와 그 이후 결과를 구분해 기록해요.
소스 버전, 입력·조작 순서, 이벤트·재생 위치, 관측한 오차와 실행하지 못한 환경을 남겨요.
전체 입력이 안정된 상태에서 `mise run check`, `mise run test`, `frontend`에서 `npx tsc --noEmit` 후 `npm run build`를 실행해요.
각 티켓의 집중 검증과 최종 전체 검사를 구분하며, 서로의 변경이 진행 중인 상태에서 전체 검사 결과를 최종 근거로 삼지 않아요.
문제가 발견되면 소유 티켓의 구현을 수정하고 영향을 받은 시나리오를 다시 검증해요.
사용자의 Discord 실험 결과가 아직 없으면 가능한 로컬·브라우저 검증은 마치되 네이티브 완료 근거가 없다는 제한을 명시해요.
이 티켓은 배포·릴리스 티켓이 아니며, 통합 검증 성공도 그 권한을 부여하지 않아요.

### 구현에서 확정한 기술적 처리

- 플레이어의 재생 의도와 `playback_suspended`를 분리하고, `playback_revision`으로 오래된 출력 준비와 종료 콜백을 거부해요.
- 현재 곡·위치·의도·대기열·반복 모드를 하나의 트랜잭션으로 저장하며, 주기 저장 간격은 4초예요.
  손상된 현재 곡 기록은 대기열·반복 모드 변경만으로 지우지 않고, 유효한 새 곡 재생으로 현재 곡을 대체할 때 저장을 다시 허용해요.
- 정상 종료는 상태를 바꾸는 작업을 정리한 뒤 마지막 권위 있는 스냅샷의 저장을 기다려요.
  저장 제한 시간을 넘기거나 실패하면 오류로 남기며 성공으로 표시하지 않아요.
- Songbird의 `driver_retry.retry_limit`은 `Some(0)`이고, 드라이버 연결 제한 시간은 15초예요.
  애플리케이션이 실패 뒤 `1, 2, 4, …, 256, 300, 300, …`초의 재시도 대기를 소유해요.
- 성공한 드라이버 재연결도 현재 기본 채널을 다시 검증해요.
  관리자 설정 저장 뒤에는 진행 중인 재시도 대기를 깨워 새 목적지를 확인해요.
- WebSocket 발행은 하나의 공통 함수에서 순번 할당과 전송을 직렬화해요.
  불완전한 상태 스냅샷의 기준점과 실시간 이벤트 커서를 분리해 대기 중인 기록·업로드 알림을 버리지 않아요.
- HTTP 상태 응답과 429 대기 시간은 재사용하지 않는 연결 수명 번호에 묶어요.
  이전 연결에서 늦게 돌아온 응답이 새 프로세스의 상태나 대기 시간을 덮어쓰지 않아요.

### 사용자 실험 절차

1. 재생 중인 곡과 위치, 대기열·반복 모드를 기록한 뒤 Discord에서 봇의 연결을 끊어요.
   기본 채널로 자동 복귀하고 같은 곡을 중단 위치에서 이어 가는지 확인해요.
2. 일시정지와 곡 없음 상태에서도 같은 조작을 반복해요.
   일시정지 위치가 유지되고 임의의 소리가 시작되지 않는지 확인해요.
3. 복구 대기 중 웹에서 일시정지·재개·탐색·건너뛰기·중지를 바꿔요.
   마지막 조작이 최종 출력과 대기열에 반영되고 이전 출력이 뒤늦게 시작하지 않는지 확인해요.
4. 격리된 테스트 환경에서 기본 채널 접근을 막았다가 복원해요.
   상한 300초 뒤에도 재시도가 계속되고 다른 채널로 우회하지 않으며, 복원 후 별도 재시작 없이 돌아오는지 확인해요.
   대기 중 기본 채널을 변경하면 새 설정을 다시 확인하는지도 관찰해요.
5. 비관리자 웹 사용자와 음성 채널 밖의 Discord 멤버가 웹 재시작 및 `/restart`를 겹쳐 실행해요.
   한 번만 교체되고, 합친 요청이 30초 기준을 연장하지 않으며, 음성 장애가 계속돼도 유한한 교체 작업 뒤에는 다시 요청할 수 있는지 확인해요.
6. 봇만 교체하는 동안 같은 웹 로그인, 기존 WebSocket, 대기열과 진행 중 다운로드가 유지되는지 확인해요.
7. 정상 체크포인트가 저장된 뒤 서로 다른 시점에 전체 앱을 강제 종료하고 다시 시작해요.
   재생·일시정지·곡 없음의 구분과 대기열·반복 모드가 유지되고 정상 저장 기준 위치 손실이 약 5초 이내인지 확인해요.

각 실험에는 실행한 소스 버전, 이벤트 시각, 봇 세대와 목적지, `BotStatus`의 `revision`·`status`·`next_retry_at`, 플레이어의 중단 여부·위치·버전을 함께 기록해요.
소리로 확인한 재개 위치와 네이티브 탐색 결과를 웹 표시와 구분해요.
토큰·JWT 쿠키·인증 헤더는 수집 결과에서 제외해요.

### 실행 검증 결과

최종 로컬 검사에서는 `mise run check`가 경고 없이 통과했고, `mise run test`에서 274개 테스트가 통과했어요.
실패하거나 무시한 테스트는 없어요.
프런트엔드는 `npx tsc --noEmit` 다음 `npm run build`가 통과했어요.

SQLite 검증은 실제 메모리 DB와 마이그레이션을 사용했어요.
원자적 저장 롤백, 구형 기록의 0초·일시정지 복원, 손상된 기록 보존, 출력 중단 중 최신 의도 저장, 종료 직전 최종 저장을 확인했어요.
종료 시 마지막 저장을 생략하거나 대기열 변경으로 손상 기록 보호를 해제하는 결함을 격리 복사본에 주입했을 때 각각 해당 회귀 테스트만 실패했고, 정상 구현에서는 통과했어요.

프런트엔드의 실제 봇 상태 저장소에 이전 연결의 늦은 HTTP 응답과 재시작 응답, 같은 연결의 오래된 revision, 이전 소켓의 늦은 종료를 입력해 현재 상태가 유지되는지 확인했어요.
연결 수명 검사를 제거한 격리 복사본에서는 오래된 응답이 현재 상태를 덮어써 검증이 실패했어요.

브라우저는 실제 웹 Router·메모리 DB·합성 인증 정보를 사용하는 로컬 전용 실행기로 확인했어요.
Discord 클라이언트는 생성하거나 실행하지 않았어요.
비관리자 재시작 버튼이 실제 `BotControl`에 접수되고 후속 요청이 `202 already_restarting`으로 합쳐지며, 접수 기준 시간이 바뀌지 않는지 확인했어요.
실제 WebSocket으로 스냅샷 뒤에 대기 중인 기록·업로드 알림과 오래된 플레이어 이벤트를 보내, 알림은 각각 한 번 전달되고 플레이어는 과거 상태로 돌아가지 않는지 확인했어요.
출력 중단 중 일시정지 조작도 반영됐어요.

한국어 데스크톱과 영어 390px 모바일 화면에서 봇 상태·재시작 제어·별도의 저장 오류·출력 복구 대기 표시를 확인했어요.
모바일에서 가로 넘침은 없었어요.
이 실행기는 네이티브 세대를 구동하지 않았으므로, 실제 봇 교체 시간이나 음성 재시도 뒤의 성공을 브라우저로 증명한 것은 아니에요.

플레이어·저장·웹 상태 동기화·네이티브 수명 경로에 독립 리뷰를 적용하고 발견한 문제를 수정했어요.
