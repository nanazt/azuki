# 재방문 로그인 유지 구현 명세

## 근거와 권한

사용자가 선택한 동작 정책은 [재방문 로그인 유지와 전체 로그아웃의 범위](../adr/0001-persistent-login-and-global-logout.md)를 따르며, 용어는 [도메인 용어](../glossary.md)를 사용해요.
[기존 JWT 구조 유지 권장안](../adr/0002-retain-jwt-for-renewable-login.md)을 현재 코드에 맞춰 구현 가능한 계약으로 구체화했어요.
기간·로그아웃 범위·기존 로그인 전환은 사용자 결정이고, 아래 경로·응답 필드·갱신 간격·연결 제어 방식은 그 결정을 만족시키기 위한 기술적 선택이에요.
이 문서 작성은 구현, 커밋, 배포 또는 원격 쓰기를 승인하지 않아요.

## 문제와 완료 결과

구현 전에는 Discord 로그인 직후 발급한 JWT와 `azuki_token` 쿠키가 24시간으로 고정되고, 사용 중에도 갱신되지 않았어요.
기존 HTTP 인증 실패는 프런트엔드의 로그인 화면 이동으로 이어졌지만, WebSocket은 연결할 때만 인증해서 이미 열린 연결에는 만료와 전체 로그아웃(Global logout)이 적용되지 않았어요.

완료 결과는 브라우저 종료나 기기 재시작을 사이에 둔 로그인 유지(Login persistence)예요.
해당 브라우저에서 인정되는 갱신이 7일간 없으면 미접속 만료(Inactivity expiration)를 적용하고, 계속 이용해도 최초 Discord 로그인부터 90일인 최대 로그인 유지 기간(Absolute session lifetime)을 넘기지 않아요.
보이는 탭은 클릭 없이도 갱신하지만 숨겨진 탭의 자동 통신은 갱신 사유가 아니에요.
전체 로그아웃은 같은 계정의 모든 브라우저와 기기, 이미 열린 WebSocket에 적용해요.

## 범위와 제외

기존 Discord OAuth, HS256 JWT, `azuki_token` 쿠키, 사용자별 `token_version`을 유지해요.
JWT 최초 발급·검증·재발급, 인증 조회, 프런트엔드 인증 수명 관리, HTTP·업로드 오류 처리, WebSocket 수명과 전체 로그아웃을 변경해요.
DB 세션 테이블, 별도 refresh token, JWT 원문을 읽거나 저장하는 프런트엔드 코드는 추가하지 않아요.
DB 스키마나 `jwt_secret` 설정 형식도 변경하지 않아요.

기기별 로그아웃, 로그인 기기 목록, Discord 토큰 갱신, 관리자 전용 재인증, 외부 API 토큰 지원은 제외해요.
기존 관리자 권한 확인과 멤버십 캐시의 갱신·빈 캐시 처리 정책은 유지해요.
로그인 종료를 Discord 음악 재생 중단과 연결하지 않아요.

## 인증 자격과 시간 계약

시간은 서버의 UTC Unix 초를 기준으로 계산해요.
7일은 604800초, 90일은 7776000초이며 달력상의 주·월로 계산하지 않아요.

JWT는 기존 `sub`, `exp`, `tv`와 함께 `session_started_at`을 필수로 가져요.
`session_started_at`은 해당 Discord 로그인으로 azuki 인증 자격을 처음 발급한 시각이며, 재발급 시 현재 시각으로 덮어쓰지 않아요.
필수 값이 없거나 형식이 잘못된 JWT를 기본값으로 보완하지 않아요.

최초 발급은 `session_started_at = now`, `exp = now + 604800`으로 처리해요.
재발급은 서명과 현재 인증 상태가 유효한 JWT에 대해서만 수행하며 다음 계약을 적용해요.

```text
absolute_expires_at = session_started_at + 7776000
new_exp = min(now + 604800, absolute_expires_at)
```

재발급에서 `sub`, 검증한 `tv`, `session_started_at`을 보존해요.
기존 JWT의 `tv`가 DB와 다른데 DB의 최신 버전을 새 JWT에 넣어서 인증을 복구하면 안 돼요.
재발급과 로그아웃이 겹쳐 늦게 도착한 쿠키가 브라우저에 저장되더라도, 로그아웃으로 폐기된 버전의 자격은 서버에서 다시 유효해지지 않아야 해요.

서버는 서명과 HS256 알고리즘, 필수 필드, 사용자 존재, `token_version`을 검증해요.
시간 검증은 `session_started_at <= now < exp <= absolute_expires_at`을 요구하며, 범위 초과나 시간 계산 오류를 거부해요.
만료 시각과 같은 시각부터 만료로 처리하고, JWT 라이브러리의 기본 허용 오차로 7일·90일 경계를 연장하지 않아요.
재발급하지 않은 구 JWT도 원래 `exp`까지는 유효할 수 있지만, 같은 90일 상한과 전체 로그아웃 검사를 계속 적용해요.

미접속 기간의 실행상 기준은 정상 클라이언트가 보이는 탭에서 갱신하고 현재 브라우저 쿠키에 적용된 서명 자격의 만료 시각이에요.
서버가 발급했더라도 응답이 유실되어 쿠키에 반영되지 않았다면 브라우저의 수명은 늘어나지 않아요.
클릭 시각이나 WebSocket 메시지 수신 시각을 추적하지 않아요.
각 브라우저는 자신에게 적용된 JWT의 `exp`를 따르며, 다른 브라우저에 발급한 JWT가 그 값을 변경하지 않아요.

쿠키는 기존 이름·경로와 `HttpOnly`, `SameSite=Lax`, 현재 HTTPS 설정에 따른 `Secure`를 유지해요.
쿠키의 `Max-Age`는 발급한 JWT의 남은 초로 설정해 90일 상한 직전에도 고정 7일 쿠키를 남기지 않아요.
토큰 원문은 응답 JSON, URL, 로그, localStorage, sessionStorage 또는 탭 간 메시지에 넣지 않아요.

## HTTP 인터페이스

| 경로 | 성공 계약 | 수명에 미치는 영향 |
|---|---|---|
| `GET /api/me` | 기존 `id`, `username`, `avatar_url`, `is_admin`에 `expires_at`, `absolute_expires_at`을 추가한 200 JSON이에요. | 현재 쿠키를 검증하고 정보를 반환할 뿐 갱신하지 않아요. |
| `POST /api/auth/refresh` | `expires_at`, `absolute_expires_at`의 200 JSON과 새 `azuki_token` 쿠키를 반환해요. | 유효한 자격만 위 시간 계약에 따라 재발급해요. |
| `POST /auth/logout` | 서버 측 전체 무효화를 저장한 뒤 쿠키를 지우고 본문 없는 204를 반환해요. | 같은 계정의 기존 버전 JWT 전체를 폐기해요. |

응답의 시간 필드는 모두 UTC Unix 초 정수이며 JWT 원문은 반환하지 않아요.
위 세 응답에는 `Cache-Control: no-store`를 적용하고, 프런트엔드 인증 조회도 캐시된 성공 응답에 의존하지 않아요.
새 갱신 경로는 기존 API 라우터의 CSRF 보호 아래에 등록하고 `X-Requested-With: XMLHttpRequest`를 요구해요.
`/auth/logout`의 기존 CSRF 검사도 유지하며, OAuth의 GET 진입·콜백 경로에는 갱신용 검사를 잘못 적용하지 않아요.
갱신 요청은 사용자 ID나 최초 로그인 시각을 본문에서 받지 않고 검증한 쿠키만 사용해요.

공통 인증 검증은 없는 사용자와 DB 장애를 구분해요.
없는 쿠키·잘못된 JWT·만료·구형 JWT·없는 사용자·폐기된 버전은 401, 접근을 거부하는 기존 멤버십 검사는 403, DB 등 서버 장애는 5xx로 전달해요.
기존 도우미가 모든 실패를 401로 바꾸는 동작을 남기지 않으며, 일반 관리자 기능의 권한 부족 403을 로그인 만료로 바꾸지도 않아요.
HTTP 도우미의 모든 호출부와 WebSocket 업그레이드 전 인증에도 같은 실패 분류를 전달해요.
이 절의 세 인증 경로는 오류 본문을 기존 `{ "error": ... }` 형식에 맞추고, 거부된 갱신에서는 새 인증 쿠키를 발급하지 않아요.
현재 비어 있는 CSRF 미들웨어의 403 본문과 로그아웃의 일반 텍스트 403도 이 계약에 맞추며, OAuth 콜백 오류 응답 전체를 재설계하는 범위로 넓히지는 않아요.

로그아웃의 계정 전체 철회 권한은 유효한 JWT, 현재 사용자와 `token_version`으로 확인해요.
자기 인증을 종료하는 동작에는 멤버십 보유나 관리자 권한을 추가 요구하지 않지만, 이를 보호 자원에 접근할 권한으로 확장하지 않아요.
버전 증가는 검증한 사용자 ID와 `tv`가 아직 DB에 일치할 때만 수행하는 단일 조건부 변경으로 처리하고, 그 변경이 실제로 만든 새 버전을 함께 반환받아요.
변경 뒤 별도 조회한 버전으로 통지하지 않으며, 조건 불일치로 변경된 행이 없으면 이미 철회된 자격의 401로 처리해요.
이는 오래 대기한 로그아웃 요청이 다른 로그아웃 뒤 새로 발급된 인증까지 다시 폐기하지 못하게 하는 기준이에요.
이미 만료되거나 폐기된 자격은 다른 유효한 로그인을 철회할 수 없고 401로 처리해요.
실패한 로그아웃은 인증 쿠키를 발급하거나 삭제하지 않아, 지연된 실패 응답이 다른 탭의 새 로그인 쿠키를 지우지 않게 해요.
CSRF 거부는 403이며, 버전 증가를 저장하지 못하면 5xx로 처리하고 성공 응답이나 철회 완료 통지를 보내지 않아요.
정상 로그아웃의 리다이렉트는 서버의 3xx 대신 프런트엔드가 204 확인 후 수행해요.

## 프런트엔드 인증 수명

인증 조회·갱신·종료를 한곳에서 관리하고, 화면별 타이머와 업로드별 로그인 리다이렉트를 중복 유지하지 않아요.
최초 `/api/me` 조회는 쿠키를 검증하며, 아직 판정하지 못한 상태·유효한 인증·인증 종료·일시적인 확인 실패를 구분해요.
네트워크 오류나 5xx를 인증 종료로 간주하지 않으며, 최초 확인이 실패하면 보호 기능을 승인하지 않은 채 오류와 다시 확인할 수 있는 경로를 제공해요.
새 사용자 표시 문구가 필요하면 기존 한국어·영어 번역 구조를 사용해요.

정상 프런트엔드는 `document.visibilityState === "visible"`일 때만 갱신을 시작해요.
최초 인증 확인 후 탭이 보이는 경우와 숨김에서 표시로 전환되는 경우에 갱신해요.
브라우저의 `online` 이벤트는 보이는 탭에서 재확인을 시작하는 신호로 사용하되, 실제 네트워크 복구와 인증 유효성은 요청 성공으로 판단해요.
이벤트가 없더라도 보이는 탭의 다음 정기 갱신이나 사용자의 재확인으로 회복할 수 있게 해요.
계속 보이는 동안에는 5분마다 갱신하며, 브라우저가 타이머를 중지했다가 돌아와도 남은 타이머만 믿지 않고 다시 확인해요.
같은 탭의 중복 이벤트와 요청은 하나의 진행 중 갱신에 합류하게 하고, 숨김·로그아웃·언마운트 후 새 갱신을 예약하지 않아요.
이미 보이는 상태에서 시작한 요청이 숨김 직후 완료되는 것은 허용하지만, 완료 콜백이 숨김 상태의 다음 갱신을 시작하면 안 돼요.

탭의 표시 상태는 정상 클라이언트의 동작 규칙이지 실제 사람이 이용하고 있다는 보안 증거는 아니에요.
서버는 클라이언트 시각이나 표시 상태 주장으로 만료를 우회하지 않아요.
만료된 JWT를 무시하고 복구하는 401 후 refresh token 흐름은 추가하지 않아요.

동일 브라우저의 탭은 쿠키를 공유하지만 서로 다른 브라우저의 미접속 기간은 독립적이에요.
여러 탭의 갱신이 겹쳐도 서로의 JWT를 철회하거나 `session_started_at`을 바꾸지 않아요.
같은 브라우저에서 응답 순서가 뒤집히면 나중에 도착한 유효한 JWT가 더 이른 `exp`로 쿠키를 덮어쓸 수 있어요.
서버가 마지막으로 발급한 값이 브라우저에도 항상 남는다는 단조 증가 계약이나 브라우저 간 분산 잠금을 추가하지 않아요.
현재 적용된 쿠키의 만료는 갱신하지 않는 `/api/me`로 다시 맞추며, 역순 응답에서도 최초 로그인 시각·90일 상한·철회 버전은 변하지 않아야 해요.
메모리에 보관한 만료 정보가 다른 탭의 갱신보다 오래될 수 있으므로, 그 정보만으로 로그아웃을 확정하지 않아요.
일반 API의 401이나 WebSocket의 인증 종료 신호를 받으면 캐시하지 않은 `/api/me`로 현재 쿠키를 한 번 확인하고, 아직 유효하면 인증을 유지해요.
동시에 발생한 확인은 합류시키고 인증 조회 자체의 실패를 다시 같은 확인으로 재귀 호출하지 않아요.
같은 탭에서 갱신이 진행 중이면 그 결과가 정리된 뒤 현재 쿠키를 확인해요.
확인 요청이 시작된 뒤 갱신이나 로그아웃의 세대가 바뀌면 오래된 확인 결과를 적용하지 않고 필요한 현재 쿠키 확인에 합류해요.
갱신의 완료를 기다리는 확인과 그 확인을 기다리는 갱신이 서로 순환 의존하지 않도록 인증 경로 자체는 일반 요청의 복구 처리와 구분해요.
탭 간 갱신 완료 통지는 현재 쿠키를 재확인하는 계기로 사용할 수 있지만, 자격 증명을 전송하거나 통지만으로 인증 성공을 확정하지 않아요.
현재 쿠키도 401이면 보호 화면·갱신·재접속을 종료하고 로그인 화면으로 이동해요.
인증 조회의 멤버십 403은 접근 거부로 처리하고, 일반 기능의 403은 해당 기능의 권한 오류로 남겨요.
네트워크·5xx 확인 실패는 자동 로그아웃이 아니라 일시적인 연결·확인 실패로 처리해요.

일반 API와 직접 파일 업로드 경로를 같은 인증 실패 처리에 연결하되, FormData의 브라우저 생성 multipart 경계를 보존해요.
실패한 재생 명령·업로드·수정 요청을 인증 복구 뒤 자동 재실행하지 않아요.
이전 요청의 완료 여부가 불명확한 상황에서 부작용을 중복 실행하는 범위를 추가하지 않아요.

로그아웃 시작 시 기존 인증 조회와 갱신의 후속 결과가 로그인 상태를 다시 설정하지 못하도록 세대를 구분해요.
204가 확인된 뒤 현재 브라우저의 보호 화면과 갱신을 종료하고 로그인 화면으로 이동해요.
5xx에서는 전체 로그아웃 성공으로 표시하거나 성공 경로로 강제 이동하지 않고 오류를 알리며 다시 시도할 수 있게 해요.
로그아웃의 401은 현재 쿠키 재확인 결과에 따라 인증 종료를 처리하되, 계정 전체 철회에 성공했다고 표시하지 않아요.
이전 인증 요청의 취소만으로 브라우저의 `Set-Cookie` 처리를 완벽히 막을 수 있다고 가정하지 않으며, 서버의 버전 검사로 철회를 보장해요.

## WebSocket과 전체 로그아웃

기존 `/ws` 경로와 Origin 허용 목록 검증을 유지해요.
연결에는 사용자 ID뿐 아니라 검증한 JWT의 `tv`, `exp`, `session_started_at`에 해당하는 인증 문맥을 보관해요.
연결 당시 자격의 만료 시각에 닫도록 예약하고, 최대 30초 간격으로 DB 버전과 기존 멤버십 정책을 다시 확인해요.
명령 승인 전에도 현재 인증을 검증해 버전 폐기를 정기 확인 시각까지 기다리지 않아요.
명령의 인증 승인 시점은 해당 명령에 대한 현재 DB 버전 조회와 시간·접근 검사가 성공한 시점이며, 그전에 무효화가 저장된 명령은 거부해요.
검증 실패 후 명령 실행이나 보호 이벤트 전송을 계속하지 않고 연결을 종료해요.
DB 장애로 검증할 수 없을 때도 명령을 승인하지 않으며 일시 장애로 연결을 종료해요.
송신과 명령 처리는 연결의 종료 상태를 공유하고, 폐기나 검증 실패를 확인한 뒤에는 새로운 명령 승인이나 이벤트 송신을 시작하지 않아요.
승인된 명령이 실행 중이거나 이미 시작한 송신이 있는 경우까지 되돌리기 위해 플레이어 실행 전체를 로그아웃과 같은 잠금에 넣지는 않아요.

전체 로그아웃은 DB의 버전 증가가 성공한 뒤 해당 사용자와 새 버전을 같은 프로세스의 연결들에 통지해요.
이 통지는 브라우저에 전달하는 `WebEvent` 스트림과 분리된 서버 내부 채널로 전달해요.
연결은 사용자 ID가 같고 통지 버전이 자신의 `tv`보다 큰 경우에만 철회하며, 다른 계정의 식별 정보나 버전을 클라이언트 이벤트로 노출하지 않아요.
각 연결은 자신보다 새 버전의 철회 통지를 받으면 정기 확인을 기다리지 않고 닫아요.
새 Discord 로그인으로 발급한 동일하거나 더 최신 버전의 연결을 오래된 통지로 닫지 않아요.
통지 구독은 초기 인증 조회 전에 시작하고, 구독 누락·지연이나 업그레이드와 로그아웃의 경합 때문에 인증이 폐기된 연결이 살아남지 않도록 초기 상태 전송 전에도 유효성을 확인해요.
통지를 놓쳤거나 수신이 밀렸다면 재검증하며, 정기 확인을 안전망으로 유지해요.
여러 서버 인스턴스 사이의 새 통지 인프라는 추가하지 않으며, 같은 DB를 공유하는 경우 다른 프로세스의 폐기는 정기 확인과 명령 전 검사로 감지해요.

인증 만료·철회·멤버십 거부로 닫는 연결에는 애플리케이션 종료 코드 4001을 사용하고, 일시 서버 장애는 1011로 구분해요.
전송 가능한 연결에서는 해당 코드를 담은 WebSocket Close 프레임을 보낸 뒤 연결을 정리하며, 소켓을 버리는 것만으로 코드가 전달된다고 가정하지 않아요.
4001은 브라우저의 현재 쿠키까지 반드시 만료됐다는 뜻이 아니라 현재 WebSocket 인증 문맥을 더 사용할 수 없다는 뜻이에요.
프런트엔드는 4001을 일반 재접속 루프에 넣지 않고 `/api/me`로 현재 쿠키를 확인해요.
다른 탭이나 보이는 탭의 갱신으로 현재 쿠키가 유효하면 재접속하고, 401·멤버십 403이면 보호 화면과 재접속을 종료해요.
1011과 네트워크 장애는 기존 제한된 지수 백오프를 유지하며, 숨겨진 탭의 재접속이나 인증 조회는 쿠키를 갱신하지 않아요.

업그레이드 전에 인증을 거부한 HTTP 401·403·5xx는 브라우저에서 4001 Close 프레임으로 관찰되지 않을 수 있어요.
연결이 열리기 전에 실패하거나 1006처럼 원인을 알 수 없는 종료가 발생한 경우에도, 백오프 재접속 전에 현재 쿠키를 갱신 없이 한 번 확인해요.
쿠키가 유효한 연결 실패만 백오프로 재시도하고, 인증 거부는 종료하며, 확인 자체의 네트워크·5xx 실패는 일시 장애로 남겨요.
Origin 거부나 전송 장애의 원인을 쿠키 만료로 단정하거나 브라우저에서 업그레이드 HTTP 상태를 직접 읽을 수 있다고 가정하지 않아요.

HTTP 갱신 때마다 정상 WebSocket을 불필요하게 끊지는 않아요.
기존 연결은 자신이 인증한 자격의 만료까지 사용하고, 종료 시 현재 쿠키가 유효하면 재연결해요.
로그아웃·언마운트 뒤 도착한 `onclose`가 새 재접속 타이머를 만들지 않도록 수명을 함께 관리해요.
연결 교체에도 세대를 부여해 이전 소켓의 open·close·error·message, 인증 확인 완료와 타이머가 현재 소켓을 덮어쓰거나 추가 연결을 만들지 못하게 해요.
로그아웃 전에 이미 승인되거나 전송된 작업·이벤트를 되돌리는 계약은 아니며, 무효화 이후의 새로운 인증 승인과 확인 실패 이후의 전송을 막는 계약이에요.

## 전환과 영향 지점

배포 시 사용자가 한 번 다시 Discord 로그인을 거치는 전환을 적용해요.
필수 `session_started_at`이 없는 기존 JWT를 거부하고, `exp - 24시간` 추정이나 기본값으로 구형 자격을 변환하지 않아요.
JWT 비밀키를 변경하거나 사용자별 DB 버전을 일괄 수정하는 데이터 작업은 필요하지 않아요.
새 백엔드와 해당 프런트엔드를 함께 배포하고 기존 백엔드 프로세스와 WebSocket을 종료해, 구형 토큰이나 폐기되지 않는 구형 연결을 제공하는 프로세스를 남기지 않아요.
구형 백엔드와 새 백엔드의 혼합 운영은 이 전환의 지원 범위가 아니에요.
교체 절차는 이전 프로세스의 종료와 업그레이드된 연결의 해제를 확인한 뒤 새 프로세스가 서비스를 제공하도록 하며, 종료 대기가 끝나지 않는 구형 프로세스를 남긴 채 성공으로 판단하지 않아요.
종료 유예는 30초로 제한하고, 기한 내 종료되지 않으면 배포 도구가 기존 프로세스를 종료시킨 뒤 해제를 확인하는 절차를 사용해요.
이는 교체 절차의 조건이며 이 문서 작성 중 배포 명령을 실행한다는 뜻은 아니에요.
배포 전부터 열린 탭의 메모리 속 구형 JavaScript는 서버 교체만으로 바뀌지 않으므로, 해당 탭은 새로고침하거나 다시 열어 새 프런트엔드를 받아야 해요.
구형 탭은 인증이 거부되지만 자동으로 새 로그인 화면까지 이동한다고 보장하지 않으며, 이 제한을 일회성 재로그인 안내에 포함해요.

새 정책 적용 뒤 구형 인증 구현으로의 롤백은 지원되는 정상 전환 경로가 아니에요.
구형 서버는 새 JWT의 추가 필드를 무시하고 7일 자격을 받아들일 수 있으며, 이전 WebSocket 인증 동작도 복구되기 때문이에요.
정책을 유지하는 롤백 대상은 이 명세의 인증 계약을 유지하는 빌드로 한정해요.
구형 구현으로의 긴급 복귀가 필요하면 정책 후퇴, 새 자격 전체의 폐기, 연결 종료와 추가 재로그인 영향을 그 작업에서 별도로 결정해야 해요.
실제 배포나 롤백 실행은 별도 권한이 필요해요.

현재 코드에서 확인한 영향 지점은 다음과 같아요.

| 위치 | 변경 책임 |
|---|---|
| `crates/azuki-web/src/auth.rs` | JWT 시간 계약, 공통 인증 문맥, 쿠키 발급·삭제, 갱신과 전체 로그아웃을 처리해요. |
| `crates/azuki-web/src/lib.rs`와 현재 `WebState` 생성 지점 | 갱신 경로의 CSRF 보호, 오류 분류, 연결 철회 통지 상태를 연결해요. |

| `frontend/src/App.tsx`, `stores/authStore.ts`, `lib/api.ts`, `hooks/useWebSocket.ts` | 인증 확인·갱신·종료와 연결 상태 전이를 통합해요. |

이는 확인된 책임 지점이며 새로운 내부 파일 분할이나 함수 이름을 강제하는 목록은 아니에요.
구현 시 변경할 공개 심볼의 참조를 확인하고 모든 호출부·픽스처를 함께 전환해요.

| 업그레이드 전 만료·철회 | 실제 연결이 열리지 않아도 쿠키 재확인 후 종료하며, 4001 프레임을 받지 못했다는 이유로 무한 재접속하지 않아요. |
| 연결 A를 B로 교체한 뒤 A의 지연된 close | B가 유지되고 중복 연결 C나 오래된 인증 상태가 생기지 않아요. |
| 프로세스 교체와 구형 탭 | 구형 자격과 기존 연결의 접근은 종료되고, 새로고침한 탭은 일회성 재로그인 후 새 정책을 사용해요. |

## 검증 방식과 실행 순서

HTTP 계약과 DB 부작용은 기존 `TestApp`의 독립 인메모리 SQLite 및 Router `oneshot` 패턴으로 검증해요.
`test_middleware.rs`의 만료·폐기·로그아웃 검사와 `test_auth_guild.rs`의 OAuth·멤버십 검증을 보존하고 새 필수 claim과 합의된 오류 계약에 맞춰 갱신해요.
시간 경계는 실제 7일·90일 대기 없이 명시적인 시각과 서명된 자격으로 검증하며, Tokio의 가상 시간만으로 `chrono::Utc`도 이동한다고 가정하지 않아요.
응답 필드만 복사됐는지 확인하는 대신, 갱신 전 만료를 지나 새 쿠키가 실제로 허용되는지와 폐기 뒤 보호 자원이 실제로 거부되는지를 확인해요.

로그아웃 저장 실패는 사용자 조회를 유지한 채 `token_version` 갱신만 실패시키는 SQLite 트리거 등으로 구분해요.
DB 전체를 닫아서 인증 조회부터 실패한 결과를 버전 증가 실패 검증으로 대신하지 않아요.
경합 검증은 실행 순서를 통제하는 작은 테스트용 지점이나 동등한 동기화를 사용하고, 무작위 동시 실행 한 번의 성공만으로 두 순서의 안전성을 주장하지 않아요.
특히 N 버전의 로그아웃 둘을 검증 이후에 대기시켰다가 하나를 완료하고 새 N+1 자격을 발급한 뒤 나머지를 진행해, 지연된 요청이 새 자격을 폐기하지 않는지 확인해요.

이 변경 이전의 `test_ws.rs`는 실제 업그레이드 없이 요청 거부만 확인했으므로, 기존 검사만으로 연결 수명이나 인증 종료를 검증했다고 보지 않아요.
루프백 임시 포트에서 실제 Router를 제공하고 실제 WebSocket 클라이언트로 초기 상태 수신, 인증 만료, 전체 로그아웃, 새 쿠키 재연결, 경합을 관찰해요.
현재 axum이 사용하는 버전과 맞는 WebSocket 클라이언트를 직접 dev-dependency로 선언하며, 의존성 추가는 워크스페이스의 기존 방식에 맞춰요.
플레이어 내부 로직 대신 연결·응답·폐기와 보호된 명령의 거부를 검증해요.
서로 독립된 철회 통지 채널과 같은 DB를 사용하는 두 Router 문맥에서도 검증해요.
첫 문맥에 연결한 뒤 두 번째 문맥으로 로그아웃해서, 같은 프로세스 통지에 의존하지 않고 새 명령을 거부하며 정기 확인의 30초 상한 안에 연결을 닫는지 확인해요.

프런트엔드는 실제 앱과 브라우저에서 두 탭·별도 브라우저 문맥, 표시·숨김 전환, 네트워크 중단·복구, 업로드, 로그아웃을 실행해요.
준비된 로컬 인증 또는 격리된 인메모리 인증 하네스에서 정식 서명 쿠키를 사용하며, 운영 DB·사용자 세션을 수정하거나 실 Discord 계정 접근을 전제로 하지 않아요.
프런트엔드에 기존 테스트 러너가 없으므로 범용 테스트 프레임워크 도입을 이 변경의 필수 작업으로 만들지 않아요.
자동화가 없는 경계는 실제 브라우저 관찰 결과로 구분해 보고해요.

시간·쿠키·인증 계약을 먼저 구현하고 이를 HTTP 경로와 픽스처에 적용해요.
합의된 HTTP와 연결 종료 계약이 준비되면 프런트엔드 수명 관리와 서버 WebSocket 처리를 각각 구현하고, 전체 로그아웃·재연결 경합을 함께 검증해요.
마지막에는 저장소 요구에 따라 `just check`, `just test`, 프런트엔드의 `npx tsc --noEmit` 이후 `npm run build`를 실행해요.
이 절은 검증 계획이며, 실제 실행 결과와 남은 검증 한계는 아래에 별도로 기록해요.

## 남은 가정과 제한

5분 갱신 간격과 30초 WebSocket 정기 확인은 로컬 구현값이며 사용자 설정 화면을 추가하지 않아요.
보이는 탭의 지속 이용 판정은 브라우저가 보고하는 표시 상태와 실제로 성공한 갱신 요청까지이며, 사용자의 시선·물리적 현존을 판별하지 않아요.
서버의 시간과 DB가 정상적인 기존 운영 조건을 따르며, 새로운 다중 서버 철회 메시지 시스템이나 시계 동기화 인프라는 범위에 넣지 않아요.
새 사용자 결정을 기다리는 차단 항목은 없으며, 구현 도중 이 가정과 충돌하는 실제 운영 요구가 발견되면 영향을 설명하고 해당 차이만 다시 판단해요.

## 구현 및 검증 결과

JWT·HTTP·WebSocket·프런트엔드 갱신 흐름과 단일 프로세스 교체 절차를 구현했어요.
새 DB 테이블이나 마이그레이션, 별도 refresh token, 구형 JWT 호환 경로는 추가하지 않았어요.
운영 전환 안내는 [README](../../README.md#login-persistence)에도 반영했어요.

| 검사 | 실행 결과 |
| --- | --- |
| `SQLX_OFFLINE=true cargo clippy --workspace --all-targets -- -D warnings` | 통과했어요. |
| `SQLX_OFFLINE=true cargo test --workspace` | 241개 테스트가 통과했어요. |
| `cargo fmt --all -- --check` | 통과했어요. |
| `SQLX_OFFLINE=true cargo build -p azuki --bin azuki` | 일반 바이너리 구성이 빌드됐어요. |
| 프런트엔드 `npx tsc --noEmit` 이후 `npm run build` | 타입 검사와 프로덕션 빌드가 통과했어요. |
| `bash -n deploy.sh` | 구문 검사가 통과했어요. |

환경에 `just` 실행 파일이 없어 `justfile`의 `check`와 `test`에 정의된 명령을 직접 실행했어요.
인증 회귀 검사에는 DB 조회 대기 중 만료, 두 로그아웃 사이의 새 로그인, 갱신·로그아웃 응답 역전, 버전 증가 실패를 포함했어요.
DB 조회 대기 중 만료 검사는 수정 전 실제로 실패했고, 조회 직후 시각을 재검증하도록 수정한 뒤 통과했어요.
실제 루프백 WebSocket 검사에는 만료 타이머, 별도 철회 채널을 사용하는 공유 DB의 30초 정기 확인, 업그레이드 경합, 두 broadcast 채널의 유실 복구, 정상 종료를 포함했어요.

격리된 인메모리 DB와 정식 서명 쿠키를 사용해 실제 프로덕션 프런트엔드 번들을 Chromium에서 실행했어요.
같은 쿠키를 공유하는 탭과 별도 브라우저 문맥의 전체 로그아웃, 다른 사용자 유지, 로그아웃 DB 실패, 503 재시도, 오프라인 복구를 확인했어요.
1초 WAV 파일의 실제 업로드와 삭제를 실행하고, 일반 API·드롭 업로드·명시적 업로드 재시도의 401 응답 뒤 인증만 재확인하며 부작용 요청을 자동 재실행하지 않는지 확인했어요.
갱신 응답 두 개의 적용 순서를 뒤집어 현재 쿠키와 `/api/me`의 만료가 일치하고 최초 시각·버전·90일 상한이 유지되는지 확인했어요.
갱신된 쿠키로 연결을 교체한 뒤 이전 소켓의 실제 close 핸들러를 늦게 실행해도 새 소켓이나 인증 상태를 바꾸지 않는지 확인했어요.
실패한 업그레이드의 1006 종료와 현재 쿠키의 실제 만료를 조합해 인증 재확인 후 로그인 화면으로 종료하고 연결을 반복 생성하지 않는지도 확인했어요.
90일 상한과 구형 JWT의 일회성 재로그인도 브라우저에서 확인했어요.

표시·숨김 정책은 실제 앱의 `document.visibilityState`를 통제해서 확인했고, 5분 갱신 타이머는 검증 중 1초로 가속했어요.
이 브라우저 실행 환경에서는 실행 문맥별 표시 상태 관찰값이 달랐으므로, 이 결과를 물리적 창 전환이나 실제 5분 대기 검증으로 간주하지 않아요.
실 Discord OAuth 로그인, 실제 기기 재부팅, 운영 Docker·SSH 배포는 수행하지 않았어요.

배포 스크립트는 격리된 Docker·SSH 명령 대역으로 실행 중·정지됨·없음 및 pull 실패·stop 실패·정지 미완료의 여섯 상태를 확인했어요.
이 검사는 명령 순서와 실패 시 새 프로세스를 시작하지 않는 동작의 증거이며, 실제 원격 배포의 증거는 아니에요.
백엔드·배포와 프런트엔드를 나눠 독립 코드 검토를 마쳤고, 발견한 문제를 수정한 최종 코드에 미해결 지적은 없었어요.
검증용 서버 예제 소스와 오디오 파일을 제거하고 소유한 브라우저 탭과 로컬 서버를 종료했어요.
