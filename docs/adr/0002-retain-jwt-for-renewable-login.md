# 자동 갱신 로그인에 기존 JWT 구조를 유지하는 권장안

인터뷰에서 사용자가 선택한 정책은 [재방문 로그인 유지와 전체 로그아웃의 범위](0001-persistent-login-and-global-logout.md)에 기록했어요.
이 문서는 그 정책과 현재 코드에 근거한 기술적 권장안이며, 사용자가 자격 증명 구조를 직접 선택했거나 구현을 승인했다는 뜻은 아니에요.

현재 인증은 JWT 서명과 만료를 검증한 뒤 DB의 사용자와 `token_version`을 매번 확인해요.
전체 로그아웃(Global logout)에 필요한 계정 단위 무효화 수단이 이미 있고, 기기별 로그아웃이나 로그인 기기 목록은 이번에 선택한 요구사항이 아니에요.
기존 JWT와 쿠키 구조를 유지하고 갱신 동작을 추가하는 방식을 권장해요.
별도의 갱신용 토큰이나 DB 세션 테이블은 선택한 정책을 충족하기 위한 필수 요소가 아니에요.

JWT에 최초 Discord 로그인 시각을 필수 정보로 포함하고, 재발급해도 그 시각을 보존해요.
각 재발급의 만료 시각은 서버 시각 기준으로 갱신 시점부터 7일과 최초 로그인부터 90일 중 이른 시각으로 제한해요.
쿠키 수명도 JWT의 남은 유효 기간에 맞추며, 서버가 만료와 무효화를 판정해요.
최초 로그인 시각이 없는 기존 JWT를 허용하는 호환 경로는 두지 않아요.
새 JWT 발급 자체가 기존 JWT를 즉시 무효화하는 것은 아니며, 기존 JWT에도 원래 만료와 90일 상한, `token_version` 검사를 적용해요.

미접속 만료(Inactivity expiration)는 현재 브라우저 쿠키에 적용된 서명 자격의 만료 시각을 기준으로 관리해요.
서버가 갱신을 수락했더라도 응답이 유실되거나 다른 유효한 갱신 응답이 나중에 적용되면, 서버의 최신 발급 시각과 브라우저에 남은 자격이 다를 수 있어요.
서버의 최종 발급 기록을 DB에 저장해 브라우저 만료가 항상 단조 증가하도록 하는 계약은 추가하지 않아요.
정상 프런트엔드는 브라우저가 표시 상태로 보고하는 이용 중인 대시보드(Active dashboard)에서만 갱신을 요청해요.
일반 HTTP 요청이나 WebSocket 통신에 일괄 갱신을 붙이지 않아요.
탭 표시 상태는 정상 클라이언트의 요청 정책이지 실제 사람이 이용하고 있다는 보안상 증거는 아니에요.
인증 자격을 탈취한 주체도 갱신을 요청할 수 있으므로, 활동 여부와 별개인 90일 상한과 전체 로그아웃의 서버 측 무효화를 유지해요.

WebSocket도 연결 당시 인증 자격의 만료 시각과 무효화 상태를 따라야 해요.
브라우저의 쿠키 갱신만으로 이미 열린 연결의 인증 정보가 바뀌지는 않으므로, 갱신된 쿠키를 사용하는 재연결과 연결 중 인증 재검증이 필요해요.
전체 로그아웃의 성공은 서버 측 무효화가 저장된 뒤에만 알리고, 실패를 무시한 채 전체 로그아웃이 완료됐다고 처리하지 않는 방향이에요.
이미 만료된 인증 자격만으로는 다른 유효한 로그인을 철회할 권한을 부여하지 않아요.

DB 기반 로그인 세션은 개별 기기 철회나 로그인 목록처럼 서버가 각 로그인을 식별해야 하는 요구가 생기면 다시 비교할 수 있어요.
현재 선택에는 그런 기능이 없으므로, 세션 테이블과 추가 자격 증명의 발급·교체·폐기 절차를 도입하지 않는 쪽을 권장해요.
기존 Discord OAuth 진입 흐름, 관리자 권한 확인, 멤버십 캐시 정책은 변경 대상으로 삼지 않아요.
로그아웃이나 로그인 만료를 Discord 음악 재생 중단과 연결하지 않아요.

판단 근거는 `crates/azuki-web/src/auth.rs`의 JWT 발급·검증과 `token_version` 검사, `crates/azuki-web/src/lib.rs`의 CSRF 보호 범위, `crates/azuki-web/src/ws.rs`의 연결 시 인증 구조예요.
이 권장안은 실행 검증이나 구현 완료를 주장하지 않아요.

API·동시성·전환·검증의 구체적인 계약은 [재방문 로그인 유지 구현 명세](../specs/persistent-login.md)에 기록했어요.
