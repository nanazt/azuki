# 음성 연결 복구와 봇 재시작

## 결정

azuki 봇이 중단되거나 음성 채널에서 연결 해제된 뒤에는 음성 연결뿐 아니라 재생 복구(Playback recovery)를 목표로 해요.
재생 중이던 곡은 중단 지점부터 자동으로 이어 재생하고, 남은 대기열을 유지해요.
일시정지 상태였다면 자동으로 소리를 내지 않고 그 상태를 유지해요.

사용자는 웹의 서버 설정과 Discord 봇 명령어 양쪽에 봇 재시작 기능을 두고, 관리자만이 아니라 누구나 사용할 수 있기를 요청했어요.
음성 연결이 끊기면 서버 설정의 기본 음성 채널로 복귀해요.
마지막으로 연결됐던 채널을 별도로 복귀 목적지로 삼지는 않아요.
사람이 Discord의 ‘연결 끊기’로 봇을 내보낸 경우도 자동 복귀 대상이에요.
따라서 이 Discord 조작은 봇을 계속 내보내 두는 제어로 사용하지 않아요.

연결 복구가 실패하면 성공할 때까지 재시도하고, 실패가 이어질수록 시도 간격을 늘려요.
재시도 간격의 상한은 5분으로 두며, 이는 총 복구 제한 시간이 아니라 계속 실패할 때 5분마다 다시 시도한다는 뜻이에요.
웹에는 연결 실패 이유와 재시도 상태를 보여줘요.
일정 시간이 지났다는 이유로 자동 복구를 포기하고 수동 조작을 요구하는 방식은 선택하지 않았어요.

봇 재시작(Bot restart)은 Discord 봇 연결과 음성 처리 작업만 대상으로 해요.
웹 서버와 로그인 및 재생 대기열은 유지해요.
웹은 기존 인증 경계를 유지하면서 로그인해 접근 가능한 모든 사용자에게 재시작을 허용하고, 비로그인 공개 제어는 만들지 않아요.
Discord에서는 설정된 서버의 일반 멤버도 관리자 여부나 음성 채널 참여 여부와 무관하게 재시작 명령어를 사용할 수 있게 해요.
기존 서버 설정의 관리자 전용 항목까지 일반 사용자에게 공개하는 것은 아니에요.

웹과 Discord를 합쳐 서버 공통으로 재시작 요청 하나만 진행해요.
진행 중 요청은 같은 작업으로 합치며, 재시작 요청을 받아들인 시점부터 30초 동안 새 재시작을 받지 않아요.
이 제한은 모든 사용자에게 동일하게 적용해요.
반복 요청으로 공동 재생을 방해할 위험을 줄이되, 30초 간격으로 재시작하는 행위까지 방지하는 정책은 아니에요.

프로세스가 갑자기 종료되면 마지막으로 저장된 위치부터 복원하며, 정상적으로 위치 저장이 이뤄지던 상황에서 최대 약 5초를 다시 듣는 것은 허용해요.
복구를 기다린 시간만큼 곡의 위치를 앞으로 보내지는 않아요.
정상적인 봇 재시작은 종료 전에 현재 재생 위치를 보존하는 방향으로 잡아요.
실제 오디오 탐색 오차나 저장 실패까지 이 허용치 안에 들어간다고 검증한 것은 아니에요.

이 기록은 구현이나 원격 변경의 승인을 뜻하지 않아요.

## 적용 경계와 기존 동작 유지

재시작 제어는 웹 서버 설정 안에 일반 사용자도 볼 수 있도록 두되, 다른 관리자 전용 설정의 접근 권한은 바꾸지 않아요.
Discord 명령어 이름은 기존 슬래시 명령어 방식에 맞춰 `/restart`를 기본으로 잡아요.
봇이 Discord 명령어를 받지 못하는 장애 상태에서는 웹 재시작 제어를 이용해요.
웹까지 중단된 상황에서 이 버튼이 azuki 전체 프로세스나 컨테이너를 되살리는 것은 이번 기능의 범위가 아니에요.

기존에 없던 빈 채널 자동 퇴장이나 복구 상태의 시간 만료 조건은 추가하지 않아요.
복구를 기다리는 동안 받은 일시정지·재생 중지 등 사용자의 최신 조작을 우선하고, 장애 전 상태로 되돌려 그 조작을 취소하지 않아요.
기본 채널이 없거나 삭제된 경우 임의의 다른 채널로 복귀하지 않아요.
채널을 지정하거나 문제를 해결하기 전에는 음성 복구가 완료됐다고 표시하지 않아요.

이번 기록은 동작 정책에 관한 결정이며, 재시도 간격의 구체적인 증가식과 저장 형식 및 작업 소유권 구조는 구현 시 기존 구조와 실행 검증에 맞춰 정해요.
로그인 및 서버 멤버십을 판정하는 기존 인증 정책 자체를 변경하지 않아요.

## 이유와 현재 근거

사용자는 봇 자체는 다시 살아나지만 음성 채널에 자동으로 돌아오지 않는 현상을 보고했어요.
채널에만 복귀하거나 듣던 곡을 처음부터 재생하는 대신, 장애 전 청취의 연속성을 유지하는 방향을 선택했어요.

현재 `crates/azuki-bot/src/handler.rs`의 `Handler::ready`와 `auto_join_default_channel`에는 설정된 기본 음성 채널로 접속하는 경로가 있어요.
이 경로가 모든 연결 해제나 봇 작업 종료 뒤의 복구를 보장하는 것은 아니에요.
`crates/azuki-player/src/controller.rs`의 `PlayerController::with_state`는 저장된 현재 곡을 재생 위치 0의 일시정지 상태로 복원해요.
따라서 현재 코드의 복원 동작과 이번에 선택한 재생 복구는 구분해요.

`crates/azuki-db/src/queries/queue.rs`의 `save_now_playing`은 현재 곡 ID와 추가한 사용자만 저장하며, 재생 위치와 재생·일시정지 구분은 저장하지 않아요.
기존에 저장하지 않은 중단 위치를 새 기능이 소급해서 알아낼 수는 없어요.
정보가 없는 기존 기록을 재생 중이었다고 추정해 자동 재개하지 않고, 기존의 0초·일시정지 복원과 새 복구 상태를 구분하는 것이 보수적인 적용 기준이에요.

`crates/azuki-bot/src/handler.rs`의 `start_bot`은 오디오 이벤트 구독 작업을 별도로 생성하지만 그 작업의 핸들을 보관하지 않아요.
같은 함수를 다시 호출하는 것만으로 이전 작업의 종료나 중복 재생 방지가 보장된다고 판단하지 않아요.

실제 장애 로그나 Discord 연결 단절 실험으로 발생 원인을 확정하지는 않았어요.
강제 종료 시 마지막 저장 위치의 허용 오차는 선택했지만, 실제 재생 위치 복구와 음성 연결 복구는 아직 구현하거나 실행 검증하지 않았어요.
Songbird의 연결 단절 시 기존 통화 객체와 트랙 종료 이벤트가 어떻게 남는지는 이번 코드 조사만으로 확정하지 않았어요.
재시도 중 중복 재생 방지, 실제 중단 위치 복구, 봇만 재시작할 때 웹 유지 여부는 구현 단계에서 실행 근거가 필요한 항목이에요.
